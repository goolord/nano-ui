nano-ui Documentation

nano-ui

An immediate-mode GUI toolkit for Haskell.

A view is a NanoUI () action that the backend re-runs every frame. Widgets return values directly (e.g. button returns Bool), input widgets take a mutable Var holding their state, and layout is a composable modifier argument. You write UIs with ordinary Haskell functions, do notation, and standard control flow (if, case, for_).

counter :: NanoUI ()
counter = row $ do
  n <- useVar (0 :: Int)
  whenM (button "-") (modifyVar n (subtract 1))
  label . T.pack . show =<< readVar n
  whenM (button "+") (modifyVar n (+ 1))

Quickstart

This guide walks you through setting up a project with nano-ui and building your first native desktop application.

Prerequisites & Installation

nano-ui requires:

  • GHC 9.10 through 9.14 (recommended: GHC 9.14)
  • Cabal 3.12+
  • SDL3 & SDL3_ttf (3.2+) when using the SDL backend (nano-ui-sdl).
  • pkg-config

Nix (Linux / macOS)

In this repository, running nix develop provides all dependencies (GHC, Cabal, SDL3, SDL3_ttf, pkg-config).

Windows

On Windows, install SDL3 and SDL3_ttf via MSYS2 UCRT64:

pacman -S mingw-w64-ucrt-x86_64-sdl3 mingw-w64-ucrt-x86_64-sdl3-ttf mingw-w64-ucrt-x86_64-pkg-config

Point PKG_CONFIG_PATH to MSYS2’s ucrt64 pkgconfig:

$env:PKG_CONFIG_PATH = "C:\msys64\ucrt64\lib\pkgconfig"

Always compile executables with -threaded. Immediate-mode GUI loops, task threads, and native window event processing require the GHC threaded runtime.

Your First Application

Create a Main.hs:

module Main (main) where

import Control.Monad (whenM)
import Data.Text qualified as T
import NanoUI
import NanoUI.Backend.Sdl

main :: IO ()
main = runSdlApp defaultSdlOptions { sdlWindowSettings = defaultWindowSettings { wsTitle = "Hello nano-ui" } } appView

appView :: NanoUI ()
appView = columnWith (gap 12 . padAll 20 . alignCenter) $ do
  heading "Counter Demo"
  
  -- Positional mutable variable initialized to 0
  n <- useVar (0 :: Int)
  
  rowWith (gap 8 . alignMid) $ do
    whenM (button "-") (modifyVar n (subtract 1))
    
    val <- readVar n
    labelWith (fontMono . fontSize 18) (T.pack (show val))
    
    whenM (button "+") (modifyVar n (+ 1))
    
  whenM (button "Reset") (writeVar n 0)

Run with Cabal:

cabal run -j1 my-app

How It Works

  1. runSdlApp initializes SDL3, creates a window with TrueType font rendering, and begins the frame event loop.
  2. columnWith / rowWith are layout containers parameterized by composable layout modifiers (gap 12 . padAll 20).
  3. useVar (0 :: Int) declares state at this position in the view hierarchy. On subsequent frames, it retrieves the existing state.
  4. button "+" renders an interactive button that returns True only in the frame it was clicked.
  5. modifyVar n (+ 1) mutates the variable. If a variable was read earlier in the frame, nano-ui safely invalidates and re-runs the pass without repeating one-shot click events.

The Frame Model

nano-ui is built on an immediate-mode execution model. Unlike retained-mode frameworks where you build an object graph of widgets and mutate them via event listeners, in nano-ui the view action re-runs every frame to describe the entire interface.

The Frame Lifecycle

Each frame proceeds through six deterministic stages:

  1. View Execution (NanoUI ()): The user action executes top-to-bottom. It emits layout nodes into an unboxed arena, reads input events, queries layout geometry from the previous frame, and reads/writes mutable Var references.
  2. Re-run Check (Self-Invalidation): If a Var is written after it was already read in the same pass, the view action is re-run once with one-shot input events cleared (preventing buttons or keystrokes from firing twice).
  3. Layout Solver: The layout tree is solved from root to leaves, determining logical rectangles for every node based on flex weights, gaps, and explicit constraints.
  4. Hit-Testing & Focus Resolution: Pointer coordinates, keyboard shortcuts, and Tab cycles are resolved against the freshly solved geometry.
  5. Damage Calculation: The new frame geometry and draw operations are diffed against the previous frame to calculate the minimal damaged bounding box.
  6. Rasterization / Paint: Only the damaged region is uploaded to the GPU / backend renderer for presentation.

Architectural Consequences

1. View Actions Can Run More Than Once Per Frame

Writing a Var that was read earlier in the same pass triggers a second pass to reconcile the UI.

Caution

Never allocate per-frame resources inside a view. For instance, liftIO (newVar x) inside a view is a critical bug—it allocates a new reference on every pass. Guard all side effects behind event checks:

whenM (button "Save") (liftIO saveDocument)

2. readVar Placement Matters

The position of readVar relative to mutating widgets impacts performance:

  • Single Pass: Reading a Var below the input widget that edits it allows the mutation and new value to resolve in a single pass.
  • Double Pass: Reading a Var above the input widget forces a second pass whenever the user types or interacts.
  • Widget-Level Repaint: Widgets bound directly to a Var without any external readVar calls only repaint that specific widget.

3. Geometry Lags One Frame

Because layout is calculated after the view action executes, respRect returns the geometry from the previous frame (empty on first appearance). When writing automated tests or positioning dynamic popups based on rects, warm up one frame before checking coordinates.

4. Idle Costs Zero CPU

When no animations, background tasks, or OS window events are pending, the backend event loop blocks on the OS event queue. The application consumes 0% CPU while idle.

State Management & Var

State in nano-ui is statically typed through explicit handles. Values are not stored in Data.Dynamic, looked up by runtime type representations, or cast out of untyped widget slots. NanoUI works identically whether state is managed via Vars, an Elm-style reducer (nano-ui-emit), or application-owned references (IORef).

The Var a Reference

A Var a is a typed mutable reference. Input widgets take the Var they display and mutate directly:

counter :: NanoUI ()
counter = row $ do
  n <- useVar (0 :: Int)
  whenM (button "-") (modifyVar n (subtract 1))
  label . T.pack . show =<< readVar n
  whenM (button "+") (modifyVar n (+ 1))

Allocating Vars

There are three ways to allocate a Var:

  1. useVar initial: Allocates a positional Var inside NanoUI for Int, Double, Float, Bool, Text, or SortCol (useEnumVar for custom Enum types). Positional Vars use a per-scope counter and key space separate from widget IDs, so conditional widgets do not shift useVar slots.
  2. newVar initial: Allocates an arbitrary Var a in IO. Allocate it during setup and store it in an application environment record passed into the view. Passing the same Var to multiple widgets naturally shares state.
  3. VarMap: One Var per key for dynamic collections (chat logs, file trees, dynamic rows). Use varAt to retrieve or create a Var, and dropVar or retainVars to clean up expired entries.

Read-Only and Projected Vars

  • constVar x: A read-only Var where writes are no-ops. Ideal for displaying derived values in input widgets and reacting via the primed Response.
  • withValue val widget: Runs a widget against a temporary Var initialized to val, returning both the widget result and the updated value.
  • Record Projections (OverloadedRecordDot): With GHC.Generics.Generic, settings.volume projects a Var Float for that specific field. Writes to settings.volume do not invalidate widgets reading settings.title!
  • Lenses & Zooming: Use zoomVar (getter/setter) or zoomVarL (lens) for custom projections.
  • Lists: forEachVar key list body provides per-element Vars that track keys across reorders.

What a Write Costs

readVar records a dependency in the current pass. When a Var changes, nano-ui classifies the write:

Write TypeDescriptionCost
Forward WriteWritten before any reads in the current pass.Single pass. Subsequent reads get the new value immediately.
Backward WriteWritten after being read earlier in the same pass.Triggers a second pass with one-shot events cleared.
Unchanged WriteNew value is == to old value (pointer checked first).No-op. Zero passes, zero repaints.

Tip

Granular Repainting: When an input widget is bound to a Var without any readVar calls anywhere in the view tree, only that individual widget’s bounds are repainted on change! Calling readVar promotes the write to a full-window repaint.

Peek and Thread-Safe Operations

  • peekVar: Reads the value of a Var without recording a dependency (useful for comparing previous vs current frame without triggering second passes).
  • Background Threads: Use readVarIO, writeVarIO, and modifyVarIO from external worker threads, then signal the UI to repaint by calling the callback obtained from askWake.

Widget Identity & Scoping

In nano-ui, widget IDs are generated deterministically based on invocation call order among siblings. Internal interactive state—such as text caret positions, active text selection, open dropdown menus, and scroll offsets—is keyed to these widget IDs.

The Identity Rules

1. Consistent Call Order

Because widget IDs count up in traversal order, the structure of calls should remain stable across consecutive frames.

2. Wrap Conditional Subtrees in scope

If an element or section is conditionally displayed, wrapping it in scope reserves a single stable slot regardless of whether the branch executes:

-- BAD: If showDetails is False, subsequent siblings shift IDs!
when showDetails $ do
  label "Details..."
  textInput detailsVar

-- GOOD: scope reserves a consistent slot in the parent hierarchy
scope $ when showDetails $ do
  label "Details..."
  textInput detailsVar

Note

useVar maintains its own dedicated counter separate from layout widget IDs. While conditional widgets alone do not shift useVar slots, conditional useVar calls themselves still require scope.

3. Reorderable Lists with withKey

When rendering collections that can be sorted, filtered, inserted, or removed, never key by list index. Wrap each item in withKey with a unique, persistent identifier (such as an item ID or UUID):

column $ for_ items $ \item -> do
  withKey item.id $ do
    row $ do
      label item.name
      whenM (button "Delete") (deleteItem item.id)

4. Retaining Dynamic State

State associated with dynamic keys is preserved while visible. For unbounded dynamic collections (such as streamed logs or ephemeral tabs), maintain row state in a VarMap and prune dead keys periodically with retainVars:

retainVars activeKeys varMap

Architecture & Application Patterns

Real-world applications built on nano-ui (such as ned, a vim-like modal editor, stronghead, a profiling debugger, and winget-gui, a Windows package manager client) converge on clean, highly reliable architectural patterns.

The Core Rule: Setup Once in IO, Then Run

Everything frame-lived is either managed via a Var or declared directly inside the view action:

main :: IO ()
main = do
  cache <- newViewCache      -- Persistent records of newVar calls & caches
  env   <- newAppEnv         -- Application state outside nano-ui
  runSdlApp defaultSdlOptions (appView env cache)

Pattern A: The winget-gui Pattern (Worker Threads + IORef)

For applications performing extensive I/O, subprocess execution, or database queries:

data Env = Env
  { envState :: IORef AppState
  , envWake  :: IORef (IO ())
  }

main :: IO ()
main = do
  stateRef <- newIORef initialAppState
  wakeRef  <- newIORef (pure ())
  let env = Env stateRef wakeRef
  runSdlApp opts (appView env)

appView :: Env -> NanoUI ()
appView env = do
  -- Install the wake callback on the first frame
  wakeCb <- askWake
  liftIO $ writeIORef env.envWake wakeCb

  -- Snapshot the state at the beginning of the frame
  state <- liftIO $ readIORef env.envState

  -- Build UI hierarchy top-to-bottom
  mainLayout state

Thread Safety with askWake

Background threads update envState atomically, then trigger a redraw:

forkIO $ do
  results <- queryPackageDatabase
  atomicModifyIORef' env.envState (\s -> (s { packages = results }, ()))
  wake <- readIORef env.envWake
  wake  -- Wake the event loop for a new frame

Pattern B: The stronghead Pattern (App Record of Vars)

For complex multi-pane applications with tightly coupled interactive state:

data App = App
  { filterText :: Var Text
  , activeTab  :: Var TabId
  , zoomLevel  :: Var Float
  , isInspecting :: Var Bool
  }

newApp :: IO App
newApp = App
  <$> newVar ""
  <*> newVar TabOverview
  <*> newVar 1.0
  <*> newVar False

The App record is passed into view functions, which read and mutate its fields directly with zero global state.

Layout Modifiers

Layout modifiers are functions of type Layout -> Layout composed with standard function composition (.).

Important

Precedence Rule: Leftmost Wins When two modifiers configure the same property, the leftmost modifier wins:

-- fixedW 200 takes effect; fixedW 100 is ignored
buttonWith (fixedW 200 . fixedW 100) "Submit"

Modifier Reference

Sizing and Expansion

  • fillW / fillH: Expands to take up all available space in the parent container along the specified axis.
  • grow: Shorthand for fillW . fillH.
  • fixedW w / fixedH h / fixedWH w h: Sets explicit logical pixel dimensions.
  • minW w / maxW w / minH h / maxH h: Constrains minimum and maximum dimensions.
  • percent p: Sets size as a percentage (0 to 100) of the parent box.
  • aspect r: Constrains the aspect ratio (width / height).

Padding and Spacing

  • padAll p: Insets all four sides by p logical pixels.
  • padXY x y: Insets horizontally by x and vertically by y.
  • padLeft / padRight / padTop / padBottom: Insets individual sides.
  • padLRTB l r t b: Explicit padding for left, right, top, and bottom.
  • gap g: Spacing between consecutive children in rows, columns, or grids.
  • tight: Removes all internal padding while preserving inter-item gap.

Alignment and Wrapping

  • alignMid: Centers children perpendicular to the flow axis.
  • alignStart / alignEnd: Aligns children to the start or end of the container.
  • alignCenter: Centers along both axes.
  • alignBaseline: Aligns text baselines across adjacent widgets.
  • wrap: Wraps overflowing children onto subsequent rows/columns (customize with lineGap and lineAlign).

Absolute Positioning and Overlays

  • pinAt x y: Positions a child absolutely at (x, y) logical coordinates within its parent container.
  • pointer PointerBlock: Consumes pointer events (preventing clicks from passing through).
  • pointer PointerPass: Transparent to pointer clicks (allows interaction with underlying elements).

Scrolling & Virtualization

nano-ui provides high-performance scroll containers supporting momentum scrolling, custom scrollbars, and virtualization for lists containing hundreds of thousands of items.

Bounded Scroll Viewports

A scroll container must have a bounded dimension along its scrolling axis:

-- Bounded vertically to 300px; fills parent horizontally
scrollWith (fixedH 300 . fillW) $ do
  column $ for_ items $ \item -> do
    label item

Warning

Giving a scroll container grow without a bounded parent can lead to unexpected collapses. Ensure the ancestor container provides a definite constraint.

2D Scrolling

For data grids, code canvases, or image viewports:

scroll2DWith (fixedWH 600 400) $ do
  largeCanvasContent

Virtualization for Massive Datasets

When rendering datasets with 10,000+ to 100,000+ rows, creating thousands of layout nodes degrades frame rates. Virtualization solves this by rendering only the rows currently visible within the scroll viewport.

Implementation Pattern

virtualizedList :: [Item] -> NanoUI ()
virtualizedList items = do
  -- Capture the widget ID of the scroller
  sid <- currentId
  
  scrollWith (fixedH 500 . fillW) $ do
    -- Query scroll metrics (current offset and viewport height)
    metrics <- getScrollMetricsUi sid
    
    let rowHeight = 28.0
        totalCount = length items
        totalHeight = fromIntegral totalCount * rowHeight
        
        -- Compute visible row slice
        firstVisible = max 0 (floor (smOffsetY metrics / rowHeight))
        visibleCount = ceiling (smViewportHeight metrics / rowHeight) + 2
        lastVisible = min totalCount (firstVisible + visibleCount)
        
        topSpacerHeight = fromIntegral firstVisible * rowHeight
        bottomSpacerHeight = fromIntegral (totalCount - lastVisible) * rowHeight
        
        visibleRows = take (lastVisible - firstVisible) (drop firstVisible items)
    
    column $ do
      -- Top spacer maintains scroll height
      when (topSpacerHeight > 0) $ spacerWith (fixedH topSpacerHeight)
      
      -- Render only active rows
      for_ visibleRows $ \rowItem -> do
        withKey rowItem.id $ do
          labelWith (fixedH rowHeight . fillW) rowItem.title
          
      -- Bottom spacer maintains scroll height
      when (bottomSpacerHeight > 0) $ spacerWith (fixedH bottomSpacerHeight)

See nano-ui-example-long-list in packages/nano-ui-demo for a complete working demo of 100,000 rows virtualized at 60 FPS.

Theming & Surface Architecture

nano-ui uses a structured surface routing architecture rather than individual per-widget CSS rules.

The Five Surfaces of a Theme

A Theme holds five distinct Style records corresponding to semantic surfaces:

  1. themeButton: Interactive controls, buttons, toggles, and dropdown triggers.
  2. themeInput: Editable text fields, search boxes, numeric inputs, and sliders.
  3. themePanel: Cards, containers, sidebars, toolbars, and background chrome.
  4. themePopup: Dropdown menus, context menus, and select popouts.
  5. themeFloatingWindow: Modals, draggable windows, and inspector dialogs.

In addition, a Theme defines semantic color roles:

  • themeAccent & themeOnAccent: Primary brand actions and focus rings.
  • themeMuted: Secondary labels, placeholders, and subtle borders.
  • themeSelection: Highlighted text and selected list rows.
  • themeFocusRing: Keyboard focus outlines.
  • Semantic Tones: themeSuccess, themeWarning, themeDanger.

Scoped Theming with styled and themed

-- Switch base theme for a subtree
themed defaultLightTheme $ do
  mainContent

Interaction States

Widgets transition through four distinct interactive states based on pointer coordinates, clicks, and disabled status:

  1. Default: Rest state. Uses styleBg, styleFg, and styleBorder.
  2. Hover: Cursor is positioned over the widget’s bounding geometry. Uses styleHoverBg.
  3. Pressed (Active): Primary mouse button is held down within the widget bounds. Uses styleActiveBg.
  4. Disabled: Interaction is suppressed by disabledWhen True. Rendering is automatically dimmed, and events are blocked.

Typography & Fonts

Font Discovery & Backend Configuration

Under the SDL backend, default TrueType fonts are bundled (Inter for proportional text). You can configure system font lookup via FontSearch:

sdlOptions
  { sdlAppFont = FontSearch ["Segoe UI", "SF Pro Text", "Helvetica Neue"]
  , sdlAppMonoFont = FontSearch ["Cascadia Mono", "JetBrains Mono", "Consolas"]
  , sdlAppFontSize = 14
  }

On Windows, font metrics are resolved with HarfBuzz shaping and FreeType rendering.

This chapter catalogs twelve non-obvious styling interactions, edge cases, and gotchas discovered in nano-ui’s layout, theming, and rendering pipelines.

buttonWith drops font flags like fontBold, fontItalic, fontUnderline, and fontTone.

Text Editing

nano-ui offers two levels of multi-line text editing:

  1. textArea: Works on a Var Text directly. Suitable for short notes, descriptions, and commit messages.
  2. textAreaDocument: Uses a Var TextDocument piece tree. Optimized for large files, editors, and code buffers with line-level immutable sharing.

Using textAreaDocument for Large Files

editorView :: Var TextDocument -> NanoUI ()
editorView docVar = do
  resp <- textAreaDocument' docVar
  
  -- Programmatic undo/redo integration
  when (textCanUndo (respId resp)) $ do
    -- Right click menu or toolbar button can invoke TextCommand
    pure ()

Text Commands & Shared Undo History

Edits performed via the keyboard, mouse selection, context menu, and programmatic calls to runTextCommand share a single undo history:

-- Run an undo command on a text editor
runTextCommand editorWid TextUndo

Directly overwriting the Var Text or Var TextDocument from outside resets the undo stack. To preserve undo across programmatic edits, issue a TextCommand instead.

Overlays, Windows & Modals

Overlays in nano-ui include modal dialogs, draggable floating windows, popups, and hover tooltips.

The Cardinal Rule: Call Overlays Unconditionally

modal, window, and popup take a Var Bool representing their open/closed state:

modal  :: Var Bool -> Text -> NanoUI () -> NanoUI ()
window :: Var Bool -> Text -> NanoUI () -> NanoUI ()
popup  :: Var Bool -> PopupConfig -> NanoUI () -> NanoUI ()

Caution

Always call overlays unconditionally every frame. Wrapping a modal call in when isShown (modal ...) shifts widget IDs for all subsequent siblings when the modal opens or closes! Overlays draw nothing when their Var Bool is False.

-- CORRECT: Called unconditionally
showConfirm <- useVar False

whenM (button "Delete File...") (writeVar showConfirm True)

modal showConfirm "Confirm Deletion" $ do
  label "Are you sure you want to permanently delete this file?"
  row $ do
    whenM (button "Cancel") (writeVar showConfirm False)
    whenM (buttonWith destructive "Delete") $ do
      deleteFile
      writeVar showConfirm False

Auto-Dismiss Behavior

By default, clicking outside an overlay, pressing the Escape key, or clicking the close button writes False to the Var Bool. For dialogs that require explicit confirmation or derived open states, pass constVar True and use modal' with respClicked.

Tooltips

Tooltips are stateless and anchor to any widget Response:

resp <- button' "Refresh"
tooltip resp "Poll the remote server for updates"

Customize placement and delay with tooltipConfigured.

Drag and Drop

nano-ui includes local drag-and-drop primitives via useDrag, useDrop, dropZone, and useReorder. Applications own the data and choose which target accepts a release gesture.

Drag Lifecycle with useDrag

Allocate a dragHandle <- newDrag once during component setup, then use it in the view:

headers <- tabBar' active documents
gesture <- useDrag dragHandle (tabHeaders headers)

useDrag tracks gesture coordinates and reports one of four phases:

  • DragStarted: Pointer exceeded the drag distance threshold.
  • Dragging: Pointer is actively moving while button is held.
  • DragReleased: User released the mouse button over a target.
  • DragCancelled: Gesture cancelled via Escape key or lost focus.

Reordering Tab Strips

case gesture of
  Just d | dragPhase d /= DragCancelled -> do
    let remaining = filter ((/= dragPayload d) . fst) (tabHeaders headers)
        slot = insertionIndex DragAxisX (tabStripRect headers)
                 (map (respRect . snd) remaining) (dragAt d)
    case slot of
      Just i | dragPhase d == DragReleased -> moveTab (dragPayload d) i
      _ -> pure ()
  _ -> pure ()

insertionIndex returns Nothing outside the strip bounds and calculates the target insertion index respecting ancestor clips.

Pane Grids (paneGrid)

Dockable, splittable multi-pane arrangements (as seen in IDEs and profiling debuggers):

grid <- paneGrid cfg
case (gesture, pgrDropTarget grid) of
  (Just d, Just target)
    | dragPhase d == DragReleased -> do
        commitPaneDrop target
  _ -> pure ()

The destination provides pgdLocation (BesidePane paneId edge or OutsideGrid edge), pgdRect, and pgdPane for custom drop validation.

Custom Canvas Drawing

For custom graphics, visualizers, audio meters, or sparklines, nano-ui provides low-level 2D vector path primitives and cached custom widget hooks.

Vector Paths with NanoUI.Path

Import NanoUI.Path qualified as P:

import NanoUI.Path qualified as P

myIcon :: NanoUI ()
myIcon = canvas (fixedWH 48 48) $ \dc -> do
  -- Draw a smooth curved shape
  drawPathWith P.NonZero (P.Solid (colorHex "#38bdf8")) $ do
    P.moveTo 10 10
    P.lineTo 38 10
    P.cubicTo 38 24 24 38 10 38
    P.closePath

Strokes and Caps

drawStrokePathWith (P.Stroke 2.0 P.CapRound P.JoinRound Nothing) (P.Solid colorWhite) $ do
  P.circle 24 24 16

Content Keys & Caching

Without a content key, custom widget draw operations are rebuilt and diffed every single frame. Providing a widgetContent key allows unchanged frames to skip rebuild and repaint completely:

-- Hash numbers or data values that the drawing depends on
let key = contentKey [round angle, round volume]

drawingVersioned key $ \dc -> do
  drawGaugeMeter dc angle volume

Caution

A content key must hash everything the drawing reads (values, colors, theme). An incomplete key will display stale pixels when unhashed state changes!

Moving Overlays & Drag Ghosts

If an overlay’s layout rectangle never changes (e.g. an element pinned at cursor coordinates via pinAt mx my), give it an explicit version that incorporates the pointer coordinates:

drawingVersioned (contentKey [round mx, round my]) $ do
  drawDragGhost

Otherwise, the engine assumes its geometry and ops have not changed since it first appeared.

nano-ui-emit: Elm-style Architecture

nano-ui-emit provides Elm-style typed messages and pure state reducers on top of nano-ui.

The NanoUIE msg a View

Instead of mutating Vars directly in views, a NanoUIE msg () view emits messages:

{-# LANGUAGE OverloadedStrings #-}

import NanoUI
import NanoUI.Emit qualified as Emit

data Msg
  = SaveDocument
  | SetVolume Float
  | Increment
  | Decrement

view :: AppModel -> Emit.NanoUIE Msg ()
view model = Emit.withNanoUI column $ do
  Emit.liftNanoUI (label "Application Settings")
  
  -- Emit on button activation
  Emit.emitWhen (button "Save") SaveDocument
  
  -- Emit on value change
  Emit.emitChanged (slider 0 100) model.volume SetVolume
  
  Emit.withNanoUI row $ do
    Emit.emitWhen (button "-") Decrement
    Emit.liftNanoUI (label (T.pack (show model.counter)))
    Emit.emitWhen (button "+") Increment

The Reducer Runner

Pair your view with a pure update reducer msg -> model -> model:

update :: Msg -> AppModel -> AppModel
update SaveDocument m = m  -- Trigger side effect via external command
update (SetVolume v) m = m { volume = v }
update Increment m = m { counter = counter m + 1 }
update Decrement m = m { counter = counter m - 1 }

main :: IO ()
main = runSdlAppReduce view update initialModel

Component Hierarchies with mapMessages

Embed reusable child components using mapMessages:

data ParentMsg = ChildMsg SubMsg | ParentSave

parentView :: SubModel -> Emit.NanoUIE ParentMsg ()
parentView sub = do
  Emit.mapMessages ChildMsg (childView sub)
  Emit.emitWhen (button "Save All") ParentSave

Messages are dispatched in order directly to the parent queue with zero intermediate wrapper allocations.

  • Compiles in seconds and produces small, completely standalone binaries.

Ideal for quick tools, game overlays, embedded environments, or minimal deployment scenarios.

Keyboard Navigation & Focus

Keyboard interaction in nano-ui covers shortcut chords, focus cycling, programmatic focus control, and IME composition.

Keyboard Shortcuts

Define keyboard chords using NanoUI.Shortcut:

-- Fires once per keystroke (ignores key repeat)
whenM (shortcutOnce (cmdOrCtrl <> key 's')) $ do
  saveDocument

-- Complex multi-modifier chords
whenM (shortcut (cmdOrCtrl <> shift <> key 'p')) $ do
  openCommandPalette

Automatic Shortcut Suppression

Shortcuts and key queries are automatically suppressed when:

  • An overlay/modal is open (unless the chord targets the modal).
  • The widget is inside a disabledWhen True subtree.
  • A focused widget claims the key (e.g. typing text in a field claims letters, arrows on a slider claim directions). Modified chords like Ctrl+Enter or Alt+Left still pass through.

Focus Lifecycle

  • Click to Focus: Clicking any focusable widget (text input, slider, select) focuses it.
  • Tab Cycling: Pressing Tab moves focus to the next widget; Shift+Tab moves to the previous widget.
  • Programmatic Focus: 
    resp <- textInput' myVar
when shouldFocus $ requestFocus (respId resp)
  • Timing: Focus takes effect at the end of the frame.

Warning

Because the node arena is reset before the view runs, checking focus at the top of a view always returns False. Query focus state at the end of the view, after the widgets have executed.

IME (Input Method Editor) Composition

Built-in text fields handle IME composition automatically. For custom widgets that consume raw committed characters from inputChars, call useInputMethod on every focused frame to position the OS candidate window correctly:

when (isFocused wid) $ do
  useInputMethod (respRect resp)

Asynchronous Work & Streams

Long-running I/O, network requests, and streaming data must not block the immediate-mode GUI frame loop. nano-ui provides structured concurrency primitives via Task and Stream.

One-Shot Background Work: Task

Allocate a task handle once during setup:

task <- newTask

Inside your view, call useTask or useTaskStatus:

-- useTask keeps the previous result while a new key runs (preventing UI flashes)
mResult <- useTask task queryKey $ \key -> do
  fetchSearchResults key

case mResult of
  Nothing      -> spinner
  Just results -> resultList results

Cancellation Semantics

  • Key Change: A task restarts automatically whenever its key changes. Ongoing work is cancelled via an asynchronous exception (bracket resources safely!).
  • Skipped Frames: If a useTask call is skipped for an entire frame (for example, if hidden inside an inactive tab), the task is automatically cancelled! To keep background downloads running while hidden, keep the useTask call outside conditional branches.

Continuous Pushing: Stream

For continuous telemetry, progress indicators, or token streaming:

stream <- newStream

-- Inside the view:
tokens <- useStream stream downloadId [] $ \push -> do
  runDownloadWithCallback push

Updates between frames coalesce automatically so high-frequency pushes never starve the UI.

Animations & Timers

nano-ui includes continuous animation channels, tweening curves, physical spring simulations, and timed wakes.

Springs and Tweens

  • animateTo: Tweens a value toward a target using an easing curve (EaseInOut, EaseOutQuad, etc.).
  • animateToA: Drives physical spring animations (presetSmooth, presetBouncy, presetStiff). Supports mid-flight retargeting without velocity hitches.
-- Smoothly animate sidebar width toward target
currentWidth <- animateTo (Tween 0.25 EaseOutQuad) targetWidth

Continuous Animations & keepAnimating

When drawing continuous animations (such as spinners or pulsing badges), call keepAnimating inside the animating widget:

pulsingBadge :: NanoUI ()
pulsingBadge = do
  t <- pulse 1.0  -- Oscillates between 0.0 and 1.0
  keepAnimating   -- Requests a frame next tick only while on screen
  drawCircleWithRadius t

Caution

Never force continuous redraws by marking the entire context dirty every frame. That creates an unpaced busy loop that drains batteries and pins CPUs.

Timers and Debounces with wakeAfter

To schedule future redraws (e.g. for clocks, timers, or tooltips):

-- Schedules a frame in 500 milliseconds
wakeAfter 500

Call wakeAfter on every frame that still requires a wake; pending wakes reset at the end of each frame.

Recurring Bugs & Fixes

Mined from the git histories and production deployments of real-world nano-ui applications (ned, stronghead, and winget-gui). Check this reference whenever diagnosing unexpected UI behavior.

1. Layout Shifting & Jitter

A label whose text changes length moves its siblings every frame

  • Symptom: A counter going 9 -> 10 -> 100, a live stopwatch, or a byte counter causes adjacent buttons to shift left and right on every tick.
  • Fix: Pin changing labels to a fixed width sized to their widest expected value: 
    labelWith (fixedW 48 . alignEnd) (fmtInt count)

Long values inside a scrolling list widen the whole list

  • Symptom: A wide row causes horizontal scrollbars to flash into existence, scrolling the entire container sideways.
  • Fix: Make cells fill their column rather than taking natural width, and enable text clipping: 
    nameLine f = rowWith (fillW . tight) . labelWith (fillW . f)

Dropdowns clipping their longest option

  • Symptom: Fixed-width select dropdowns truncate items like "Drive C: \ 412 GB free".
  • Fix: Measure option text lengths using font metrics: 
    let w = maximum (0 : map (lineWidth fm) options) + 56
selectWith (fixedW w) options selVar

2. Double Borders & Box-in-a-Box Chrome

  • Symptom: Nesting panel, card, or scrollArea inside modals, popovers, or inspector panes creates redundant double borders and nested boxes.
  • Fix: Only one container level should own surface chrome:
    • Give outer dialogs padAll 0 and pad inner containers, OR
    • Strip chrome from the inner container: 
      styled (inputStyle (background colorTransparent . borderWidth 0)) ...
    • Between adjacent sections, draw a single separator rather than opposing borders.

3. Text Metrics & Pixel Grid

Glyphs drifting over long text runs

  • Symptom: fmAdvance multiplied by character count drifts ~1px every 30 characters compared to actual rendered text.
  • Fix: Always measure runs using lineWidth fm run (which accounts for HarfBuzz kerning and unrounded fractional advances).

Text shimmering at fractional DPI scales (125%, 150%)

  • Symptom: Rows of 22.4px alternate 22px and 23px apart, producing shimmering during scrolling.
  • Fix: Snap coordinates to the device pixel grid using fmSnapScale: 
    snap v = let k = max 1 (fmSnapScale f) in fromIntegral (round (v * k) :: Int) / k

4. Stale Cached Drawings

  • Symptom: A custom-drawn widget (e.g. table sort arrow or audio visualizer) freezes or shows outdated information.
  • Fix: The widgetContent key is missing an input! The key must cover every variable, color, viewport dimension, and animation channel the drawing reads.

5. Input Ordering & Focus

Asking focus questions at the top of the view

  • Symptom: Global shortcuts (Ctrl+A, Delete) fire while the user is actively typing inside a text field.
  • Fix: The node arena is reset before the view action runs. Calling isFocused or checking text editing state at the top of the view always returns False. Place keyboard shortcuts and focus queries at the end of the view, after widgets have executed.

Escape claimed by text inputs

  • Symptom: Pressing Escape inside a search box fails to clear a modal or dismiss a dropdown.
  • Fix: Text fields do not claim Escape. Give Escape handlers their own distinct conditional branch separate from inputChars suppression.

Quick Pitfalls Checklist

  • liftIO (newVar ...) inside a view — allocates every pass. Move to setup.
  • Unguarded side effects — view re-runs. Wrap in whenM (button ...).
  • Conditional widgets or useVar without scope — shifts sibling IDs.
  • Overlays called conditionally instead of unconditionally with Var Bool.
  • useTask inside a hidden tab — task is cancelled when skipped.
  • Writing freshly computed NaN to a Var Float — causes infinite redraw loop (NaN /= NaN).
  • Missing -threaded in executable cabal options.
  • Touching Context from a background thread — call askWake instead.
