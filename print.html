nano-ui Documentation

nano-ui

An immediate-mode GUI toolkit for Haskell.

A view is a NanoUI () action that the backend re-runs every frame. Widgets return values directly (button returns Bool), input widgets take a mutable Var holding their state, and layout is a composable modifier argument. You write UIs with ordinary Haskell functions, do notation, and standard control flow (if, case, for_).

counter :: NanoUI ()
counter = row $ do
  n <- useVar (0 :: Int)
  whenM (button "-") (modifyVar n (subtract 1))
  label . T.pack . show =<< readVar n
  whenM (button "+") (modifyVar n (+ 1))

Quick Start

This guide sets up a project and builds a small windowed application. It should take about ten minutes. The tutorials take it from there.

Prerequisites

  • GHC 9.10 through 9.14 (development uses 9.14)
  • Cabal 3.12+
  • SDL3 and SDL3_ttf 3.2+ for the SDL backend
  • pkg-config

Your first application

Create Main.hs:

module Main (main) where

import Data.Text qualified as T
import NanoUI
import NanoUI.Backend.Sdl

main :: IO ()
main =
  runSdlApp
    defaultSdlOptions
      { sdlWindowSettings =
          defaultWindowSettings {wsTitle = "Hello nano-ui"}
      }
    appView

appView :: NanoUI ()
appView = columnWith (gap 12 . padAll 20 . alignCenter) $ do
  heading "Counter Demo"

  -- State at this call site; allocated on the first frame only.
  n <- useVar (0 :: Int)

  rowWith (gap 8 . alignMid) $ do
    whenM (button "-") (modifyVar n (subtract 1))

    value <- readVar n
    labelWith (fontMono . fontSize 18) (T.pack (show value))

    whenM (button "+") (modifyVar n (+ 1))

  whenM (button "Reset") (writeVar n 0)

Run it:

cabal run -j1 my-app

-j1 is the recommendation for this repository and for memory-constrained machines; a normal project can use cabal’s defaults.

How it works

  1. runSdlApp initializes SDL3, creates a window with TrueType font rendering, and starts the frame loop.
  2. columnWith / rowWith are layout containers. Their argument composes layout modifiers (gap 12 . padAll 20); the leftmost modifier wins when two set the same property.
  3. useVar (0 :: Int) declares state at this position in the view. On later frames it retrieves the existing value; the initial value is used only on the first frame.
  4. button "+" draws an interactive button and returns True only on the frame it is activated.
  5. modifyVar n (+ 1) updates the value. Reading n below the buttons means the label shows the new value in the same pass; reading it above them would cost a second pass.

The view runs every frame, so ordinary side effects must be guarded by an event (whenM (button "Save") save), and per-frame resources must not be allocated inside it. State & Var explains both rules in depth.

How to read the code

Most of the code in these chapters is ordinary Haskell: data types, pure helpers, and functions that take a Var or a model and return NanoUI (). The only unusual idea is the frame:

  • The view action runs every frame. A button call draws the button and reports what happened to it in this frame; there is no event handler to register.
  • Anything that must survive between frames lives in a Var (useVar for ordinary values, newVar for application-owned state), an Elm-style model, or a reference you own.
  • A side effect belongs inside an event check, never after a bare widget call. whenM (button "Save") save is correct; button "Save" >> save would save every frame.

State & Var explains the frame model in more depth. For now, the three rules above are enough to follow along.

Tutorial 1: Build a Todo List

This tutorial builds a todo list with the features that make a list worth using:

  • add items with Enter or a button
  • edit an item in place
  • mark items done
  • filter by all / active / done
  • reorder items, keeping each row’s local state with it
  • clear completed items

The complete program is packages/nano-ui-demo/examples/TodoList.hs. Run it with:

cabal run nano-ui-example-todo-list

1. The data model

A todo item needs an identity that outlives its position. Positions change when an item is added, removed, filtered, or reordered; the id does not. Every widget or Var that belongs to a row is keyed by that id later.

data Todo = Todo
  { todoId :: !Int
  , todoText :: !Text
  , todoDone :: !Bool
  }
  deriving (Eq, Generic)

-- | The items in order, and the id the next one gets.
data Todos = Todos
  { todoItems :: ![Todo]
  , todoNext :: !Int
  }
  deriving (Eq, Generic)

newtype App = App {appTodos :: Var Todos}

The list lives in a Var Todos. That is not a type useVar can allocate, so it is created once during setup with newVar:

newApp :: IO App
newApp =
  App
    <$> newVar
      ( Todos
          [ Todo 0 "Read the header" True
          , Todo 1 "Water the plants" False
          , Todo 2 "Edit me, then delete the first row" False
          ]
          3
      )

newVar returns IO (Var a). Allocating it in main and passing it into the view is what makes it survive between frames. Allocating a Var inside the view would create a fresh one on every pass.

Both records derive Generic; with OverloadedRecordDot, app.appTodos.todoItems is a Var [Todo] projecting just that field. Editing the list does not repaint a widget that reads only todoNext.

2. The application shell

main :: IO ()
main = do
  app <- newApp
  runSdlApp
    defaultSdlOptions
      { sdlAppShouldQuit = pressedOnceIn KeyEscape
      , sdlWindowSettings =
          defaultWindowSettings {wsTitle = "Todo list", wsSize = Size 720 560}
      }
    (todoApp app)

runSdlApp takes the options and the view. The view is not called once: the backend calls it every frame, and it must describe the whole window each time.

todoApp :: App -> NanoUI ()
todoApp app = do
  let
    items = app.appTodos.todoItems
  draft <- useVar ""
  filt <- useEnumVar All
  columnWith (padAll 20 . gap 12 . fillW . fillH) $ do
    heading "Todos"
    newItemRow app.appTodos draft
    filterRow items filt
    todoList items filt

The view’s local state (the draft text and the current filter) is allocated with useVar and useEnumVar. Both are positional: they are identified by their call site, so they need no setup and no record field.

columnWith (padAll 20 . gap 12 . fillW . fillH) is a layout argument. Modifiers compose left to right, and the leftmost one wins when two set the same property.

3. Adding an item

The input row has three jobs: draw the field, draw the button, and decide whether this frame is an “add” frame.

newItemRow :: Var Todos -> Var Text -> NanoUI ()
newItemRow todosVar draft = rowWith (tight . gap 8 . alignMid . fillW) $ do
  inputR <-
    textInputConfigured'
      defaultTextInputConfig {ticPlaceholder = "What needs doing?"}
      draft
  clicked <- button "Add"
  text <- T.strip <$> readVar draft
  when ((clicked || respSubmitted inputR) && not (T.null text)) $ do
    modifyVar todosVar (\(Todos xs n) -> Todos (xs <> [Todo n text False]) (n + 1))
    writeVar draft ""
    requestFocus (respId inputR)

Details:

  • The primed widget returns a Response. textInputConfigured' reports the widget’s identity, rectangle, hover and click state, and whether Enter was submitted (respSubmitted). button already returns the one Bool this row needs.
  • readVar draft sits below the field that edits it. The field’s write lands first, then the read sees the new text in the same pass. Reading above an editing widget forces a second pass.
  • modifyVar reads the latest value. Two changes in one frame both apply; the append does not lose one.
  • The field is cleared and focused again, so the next item can be typed immediately. requestFocus takes effect at the end of the frame.

Note

The when guard around the mutation is not optional. The view runs every frame, so an unguarded modifyVar would add an item on every pass. Event-driven work goes inside whenM (button ...) or a condition like the one above.

4. Filtering and a derived count

The filter is a local value with three states. useEnumVar accepts any Enum/Bounded type and keeps the chosen value across frames:

data Filter = All | Active | Done
  deriving (Eq, Show, Enum, Bounded)

matches :: Filter -> Todo -> Bool
matches All _ = True
matches Active t = not (todoDone t)
matches Done t = todoDone t

filterRow :: Var [Todo] -> Var Filter -> NanoUI ()
filterRow items filt = rowWith (tight . gap 12 . alignMid . fillW) $ do
  -- A header for every filter, as a segmented control.
  boundedTabBarConfigured
    defaultTabsConfig {tabsStyle = TabSegmented}
    (T.pack . show)
    filt
  flex
  todos <- readVar items
  let
    left = length (filter (not . todoDone) todos)
  labelWith
    (tight . alignMid . fontMuted)
    (T.pack (show left) <> if left == 1 then " item left" else " items left")
  disabledWhen (left == length todos) $
    whenM (button "Clear completed") (modifyVar items (filter (not . todoDone)))

boundedTabBarConfigured draws a segmented control over every constructor of Filter; the label function is show. The count is derived: it is computed from the list every frame, never stored in a second Var that could drift. disabledWhen dims the clear button and blocks its events without removing it from the layout.

5. Rows own their state

Each row needs local state (whether it is being edited and the draft of its text), but the list can be filtered and reordered underneath it. Per-row state must follow the item, not the row’s position on screen.

todoList :: Var [Todo] -> Var Filter -> NanoUI ()
todoList items filt = do
  shownFilter <- readVar filt
  scrollWith (grow . fillW) $
    columnWith (tight . gap 6 . fillW) $
      withElemVars todoId items $ \todos at -> do
        let
          shown = filter (matches shownFilter) todos
        -- Each row gets its visible neighbours, so Up and Down skip rows
        -- the filter hides.
        forM_
          (zip3 shown (Nothing : map Just shown) (map Just (drop 1 shown) <> [Nothing])) $ \(todo, above, below) ->
          withKey (todoId todo) (todoRow items (at todo) above below)
  • withElemVars todoId items gives the current list and a function at :: Todo -> Var Todo. at todo is a Var addressed by the item’s id, so it survives a reorder or a filter change.
  • withKey (todoId todo) does the same for the row’s widget state and its positional useVar slots. Without the key, deleting the first row would move every later row’s caret, edit flag, and half-typed draft one position up.
  • matches filters the rows. The neighbours (above, below) are passed in so the Up/Down buttons can skip rows that the filter hides.

Here is the row itself, trimmed to the essential structure:

todoRow :: Var [Todo] -> Var Todo -> Maybe Todo -> Maybe Todo -> NanoUI ()
todoRow items todo above below = do
  -- Local state, kept under this row's key.
  editing <- useVar False
  focusPending <- useVar False
  draft <- useVar ""
  t <- readVar todo
  isEditing <- readVar editing
  let
    tid = todoId t
    save = do
      writeVar todo.todoText =<< readVar draft
      writeVar editing False
  when isEditing (whenM takeEscape (writeVar editing False))
  rowWith (tight . gap 8 . alignMid . fillW) $ do
    checkboxWith alignMid "" todo.todoDone
    -- The label and the field swap places, so they share a scope.
    scope $
      if isEditing
        then do
          fieldR <- textInput' draft
          -- Focus can only move to a widget declared in the pass that asks,
          -- and the field first appears in the pass after Edit was clicked,
          -- so the request waits in a Var.
          whenM
            (readVar focusPending)
            (requestFocus (respId fieldR) >> writeVar focusPending False)
          when (respSubmitted fieldR) save
        else
          labelWith
            (fillW . alignMid . (if todoDone t then fontStrike . fontMuted else id))
            (todoText t)
    whenM (button (if isEditing then "Save" else "Edit")) $
      if isEditing
        then save
        else
          writeVar draft (todoText t)
            >> writeVar editing True
            >> writeVar focusPending True
    disabledWhen (null above) $
      whenM (button "Up") (forM_ above (modifyVar items . swapIds tid . todoId))
    disabledWhen (null below) $
      whenM (button "Down") (forM_ below (modifyVar items . swapIds tid . todoId))
    whenM
      (styled destructive (button "Delete"))
      (modifyVar items (filter ((/= tid) . todoId)))

Three details make this work:

  1. scope around the label/field swap. Only one of the two branches runs on a given frame. Without scope, the widgets after the branch would shift ids whenever the row enters or leaves edit mode. scope reserves one slot either way. (The useVar slots inside the row are stable because the whole row is under withKey.)
  2. A delayed focus request. requestFocus can only target a widget declared in the same pass. The field first appears in the pass after Edit was clicked, so the request waits in focusPending until the field exists.
  3. Editing writes back into the item’s Var. todo.todoText projects one field; todo.todoDone does too, which is why the checkbox can edit it in place. Saving writes the draft and clears the edit flag.

6. Reordering by id

Up and Down need to swap two items wherever they are in the full list. Swapping by id keeps the operation correct even though the visible list is filtered:


-- | Swap the places of two items, by id.
swapIds :: Int -> Int -> [Todo] -> [Todo]
swapIds a b xs = map pick xs
 where
  byId i t = fromMaybe t (find ((== i) . todoId) xs)
  pick t
    | todoId t == a = byId b t
    | todoId t == b = byId a t
    | otherwise = t

The row’s local state follows the id, not the index, so the edit flag and draft travel with the item. This is the payoff for the keys in the previous section.

7. Keyboard behaviour

Enter in the new-item field adds an item because respSubmitted reports it. Escape cancels an edit:

  when isEditing (whenM takeEscape (writeVar editing False))

takeEscape claims the press for this handler, so later Escape handlers in the view (an open popup or a second takeEscape) do not also act on it. The window’s quit policy is separate: the example sets sdlAppShouldQuit = pressedOnceIn KeyEscape, so Escape still quits the application unless the application chooses another policy (or handles Escape itself in the view and leaves the predicate off).

For the full shortcut model (shortcut, shortcutOnce, menu bindings, and how focused widgets claim keys), see Keyboard, Focus & IME.

Tutorial 2: Build a Notepad

A menu bar, file dialogs, a text document with undo, a status bar, and a prompt before losing unsaved work. It covers menus, dialogs, and close confirmation.

The complete program is packages/nano-ui-demo/examples/Notepad.hs. Run it with:

cabal run nano-ui-sdl-notepad

1. State that belongs to the session

A text document is not a type useVar can hold, and the editor’s identity must outlive any single frame, so both live in a record allocated once:

data NotepadState
  = NotepadState
      !(Var TextDocument)
      !(Var WidgetId)
      !(Var (Maybe FileDialogId))
      !(Var (Maybe FileDialogId))

-- | A notepad's private document and dialog state. Allocate one per
-- instance before starting the SDL session, and draw it with 'notepadUi'.
newNotepad :: IO NotepadState
newNotepad =
  NotepadState
    <$> newVar emptyDocument
    <*> newVar (WidgetId 0)
    <*> newVar Nothing
    <*> newVar Nothing

The menu state, path, dirty flag, zoom, and transient messages are simpler and can be useVars inside the view. The rule of thumb: allocate in IO what other code needs a handle to (a document, a task, a dialog), and use useVar for view-local state.

2. Close confirmation

By default the window closes as soon as the close button is pressed. A notepad needs to intercept that and ask about unsaved changes, so the window is created with wsExitOnCloseRequest = False:

main :: IO ()
main = do
  state <- newNotepad
  runSdlApp
    defaultSdlOptions
      { -- A close request goes to the view, which may ask about unsaved changes.
        sdlWindowSettings =
          defaultWindowSettings
            { wsTitle = "nano-ui Notepad"
            , wsSize = Size 1000 720
            , wsExitOnCloseRequest = False
            }
      , sdlAppTheme = Just tomorrowNightMinDarkTheme
      }
    (notepadUi state)

With exit-on-close off, winCloseRequested <$> askWindow reports the request inside the view, where it can open a confirmation modal instead of quitting:

  item (winCloseRequested <$> askWindow) exitApp

exitApp quits immediately when the document is clean, and opens a modal when it is not. The full wiring is in section 7.

3. A menu bar from primitives

There is no opaque menuBar widget. A menu bar is a row of menuButton's, each paired with a popup' anchored to the button’s rectangle. That is a feature: the menu’s contents are ordinary NanoUI ().

The helper below mirrors the one in the notepad source. openMenu holds the label of the open menu (empty when all are closed):

menuBar :: Var Text -> [(Text, NanoUI ())] -> NanoUI ()
menuBar openMenu entries = do
  current <- readVar openMenu
  rowWith (tight . fillW . fixedH 28) $ do
    for_ entries $ \(menuLabel, body) -> do
      let
        isOpen = current == menuLabel
      -- Each title covers the bar's height, its text in the middle.
      btn <- menuButtonWith' fillH menuLabel isOpen
      when (respClicked btn) (writeVar openMenu (if isOpen then "" else menuLabel))
      when
        (not isOpen && not (T.null current) && respHovered btn)
        (writeVar openMenu menuLabel)
      let
        cfg =
          (defaultPopupConfig (AnchorRect (respRect btn)))
            { cfgPlacement = PlacementBelow
            , cfgOffset = 0
            }
      -- The open flag is derived from the open menu's name, so the popup
      -- gets a constant and closing it is written here.
      (popupResp, _) <- popup' (constVar isOpen) cfg (columnWith (tight . gap 0) body)
      when (respClicked popupResp) (writeVar openMenu "")

popup' needs a Var Bool for whether it is open, but the state is derived from openMenu (“is this label the open one?”). constVar isOpen supplies a read-only Var; writes to it are no-ops. When the popup reports a click, the code writes the real state (openMenu) instead.

Important

Call overlays unconditionally. popup' is called for every title on every frame, even when closed; it draws nothing while closed. Wrapping it in when isOpen would change the widget ids of later siblings each time a menu opens.

4. Commands, menus, and shortcuts

Each menu row is a menuItem / menuItemShortcut. The row reports activation, and the action runs in the same frame:

    item menuRow action = whenM menuRow (writeVar openMenu "" >> action)

    fileMenu = do
      commandItem newCmd
      commandItem openCmd
      commandItem saveCmd
      commandItem saveAsCmd
      menuSeparator
      commandItem exitCmd

(newDocument, openDocument, saveDocument, and exitApp are ordinary NanoUI () actions defined in the full source; openDocument starts a non-blocking askOpenFileDialog.)

menuItemShortcut shows the chord label and binds it while the menu is open. To make the command work with the menu closed, bind the same chord with shortcut outside the menu:

  for_ [newCmd, openCmd, saveCmd, saveAsCmd, exitCmd] $
    \(_, chord, action) -> item (shortcut chord) action

Only the first binding of a chord in a frame fires, so the menu row and the view binding never both run it. The menu row is declared first, so while the menu is open its row wins.

Two more details from the source:

  • menuItemDisabled "Undo" draws a dimmed row that cannot be clicked. The Edit menu chooses between a real item and a disabled one by checking textCanUndo / textCanRedo.
  • An action that opens a file dialog writes the new FileDialogId into a Var; dialogs are non-blocking, so the view is not interrupted.

5. Opening and saving files

The SDL backend’s file dialogs are asynchronous. useFileDialog polls a Var (Maybe FileDialogId), consumes the finished result once, and restores focus afterwards:

  useFileDialog openDlg $ \chosenPaths ->
    for_ (listToMaybe chosenPaths) $ \filePath -> do
      loaded <-
        liftIO (try (BS.readFile filePath) :: IO (Either SomeException BS.ByteString))
      case loaded of
        Left _ -> writeVar statusMsg ("Could not open " <> T.pack filePath)
        Right raw -> do
          -- Lenient decode: malformed bytes become U+FFFD instead of throwing.
          writeVar doc (textDocument (TE.decodeUtf8With (\_ _ -> Just '\xFFFD') raw))
          -- A new editor, without the old document's caret and undo history.
          modifyVar docGen (+ 1)
          writeVar docPath (T.pack filePath)
          writeVar docDirty False
          writeVar statusMsg ("Opened " <> T.pack filePath)
  useFileDialog saveDlg $ \chosenPaths ->
    for_ (listToMaybe chosenPaths) $ \filePath -> do
      saved <- writeDocument filePath =<< readVar doc
      if saved
        then do
          writeVar docPath (T.pack filePath)
          writeVar docDirty False
          writeVar statusMsg ("Saved " <> T.pack filePath)
        else writeVar statusMsg ("Could not save " <> T.pack filePath)

Starting a dialog returns an id:

writeVar openDlg . Just =<< askOpenFileDialog defaultFileDialogOptions
writeVar saveDlg . Just =<< askSaveFileDialog defaultFileDialogOptions

writeDocument is ordinary Haskell around liftIO, because file I/O is an event-driven side effect:

writeDocument :: FilePath -> TextDocument -> NanoUI Bool
writeDocument filePath doc = do
  result <-
    liftIO
      ( try (BS.writeFile filePath (TE.encodeUtf8 (documentText doc))) ::
          IO (Either SomeException ())
      )
  pure (isRight result)

documentText is the only conversion from the document to a Text; editing works on the document directly and never rebuilds the whole string per keystroke.

6. The editor

textAreaDocument edits a Var TextDocument with line-sharing and an undo history. The primed variant supplies the Response the application needs:

    editorResp <-
      withKey gen $
        textAreaDocumentWith'
          (grow . minW 240 . minH 160 . fontSizeScale zoomVal)
          doc
    -- respChanged reports an edit, not a caret move.
    when (respChanged editorResp) (writeVar docDirty True)
    writeVar editorId (respId editorResp)
  • withKey gen changes the editor’s key when the document is replaced. A new document gets a fresh caret, selection, and undo stack. Merely editing does not change gen.
  • respChanged reports an edit, not a caret move. Marking dirty on caret movement would make a read-only inspection look like a modification.
  • respId is saved for menu commands. The menus can later call runTextCommand editor Undo and friends.

fontSizeScale zoomVal zooms the text without touching the document. The zoom commands are ordinary modifyVar calls clamped to a sane range.

7. Dirty state, title, and the close prompt

The title is derived every frame from the path and the dirty flag, and set declaratively:

    path <- readVar docPath
    dirty <- readVar docDirty
    let
      name = (if T.null path then "Untitled" else path) <> (if dirty then " *" else "")
setWindowTitleUi (name <> " - nano-ui Notepad")

setWindowTitleUi is a no-op when the title has not changed, so it is safe to call unconditionally. The imperative window actions (resizeWindowUi, maximizeWindowUi) are different: they run on every call and belong behind events.

The close request and the modal fit together like this:

    exitApp = do
      dirty <- readVar docDirty
      if dirty then writeVar aboutOpen False >> writeVar confirmExit True else quitUi

-- ...inside the view, called unconditionally:
  modal confirmExit "Unsaved changes" $ do
    label "Discard the changes to this document and exit?"
    rowWith fillW $ do
      flex
      whenM (button "Discard") quitUi
      whenM (button "Cancel") (writeVar confirmExit False)

There is one modal at a time: opening the exit prompt closes the About modal first. Overlay state is a Var Bool, and the modal call itself is unconditional.

8. Undo, redo, and the rest of the editing commands

The document keeps one undo history shared by typing, context-menu actions, and programmatic commands. The Edit menu reads the history state and runs commands by widget id:

    editMenu = do
      editor <- readVar editorId
      canUndo <- textCanUndo editor
      canRedo <- textCanRedo editor
      if canUndo
        then editItem "Undo" (cmdOrCtrl <> key 'z') Undo
        else menuItemDisabled "Undo"
      if canRedo
        then editItem "Redo" (cmdOrCtrl <> shift <> key 'z') Redo
        else menuItemDisabled "Redo"
      menuSeparator
      editItem "Cut" (cmdOrCtrl <> key 'x') Cut
      editItem "Copy" (cmdOrCtrl <> key 'c') Copy
      editItem "Paste" (cmdOrCtrl <> key 'v') Paste
      menuSeparator
      editItem "Select All" (cmdOrCtrl <> key 'a') SelectAll

TextCommand covers InsertText, Delete, Move, Select, Replace, ReplaceAll, Undo, Redo, Cut, Copy, Paste, and SelectAll. Using commands rather than writing the Var keeps undo intact; assigning a freshly computed TextDocument to doc clears the history.

Tip

A focused text editor claims its own editing chords (Ctrl+Z, Ctrl+X, and so on) before the application’s shortcuts see them. The menu items still work because they are explicit commands, and the top-level bindings are a fallback for when focus is elsewhere.

Tutorial 3: Live Data & Background Work

A frame must finish quickly. Searching a database, downloading a file, or waiting for a sensor cannot happen inside the view, or the window stops responding while the work runs. nano-ui moves that work to worker threads behind two handles, Task and Stream, and wakes the frame loop when there is something new to draw.

This tutorial builds three small panes from packages/nano-ui-demo/examples/Tasks.hs plus the live chart from LiveChart.hs. Run them with:

cabal run nano-ui-example-tasks
cabal run nano-ui-example-live-chart

Important

Compile with -threaded. The frame loop sleeps while a job runs, and the job runs on a Haskell thread while the loop is blocked.

1. Allocate handles once

A Task runs one typed job; a Stream carries one typed push channel. Both are created during setup, like a Var:


-- | One handle per job. The types fix each job's key and result.
data App = App
  { appSearch :: !(Task Text [Text])
  , appFlaky :: !(Task Int Text)
  , appProgress :: !(Stream () Int)
  }

newApp :: IO App
newApp = App <$> newTask <*> newTask <*> newStream

The key type and result type are fixed by the handle. That means a task cannot accidentally be reused for a different job, and no message type is erased at runtime.

2. A background search

The query field is debounced: searchInput' reports respChanged once typing pauses, not on every keystroke. The committed query becomes the task’s key:

searchCard :: App -> NanoUI ()
searchCard app = do
  query <- useVar ""
  committed <- useVar ""
  resp <- searchInput' "Find a word" query
  -- searchInput' reports a change once typing pauses, so a fast typist
  -- starts one job, not one per keystroke. Keying by the query itself would
  -- also work; each new key would just kill the job before it.
  when (respChanged resp) (writeVar committed =<< readVar query)
  key <- readVar committed
  status <- useTaskStatus (appSearch app) key (slowSearch key)
  -- While a new query runs, TaskRunning carries the previous results, so
  -- the list stays put instead of flashing empty.
  let
    (hits, running) = case status of
      TaskRunning previous -> (fromMaybe [] previous, True)
      TaskDone found -> (found, False)
      TaskFailed _ previous -> (fromMaybe [] previous, False)
  rowWith (tight . gap 8 . alignMid) $ do
    -- The spinner comes and goes, so it sits in a scope: the label after it
    -- keeps its widget id either way.
    scope (when running spinner)
    muted
      ( T.pack (show (length hits))
          <> " matches"
          <> if running then " (searching...)" else ""
      )
  rowWith (wrap . gap 6 . fillW) $
    forM_ (take 24 hits) $
      \w -> withKey w (label w)

slowSearch is ordinary blocking IO:

slowSearch :: Text -> IO [Text]
slowSearch q = do
  threadDelay 500000
  let
    found = filter (T.isInfixOf (T.toLower q)) wordList
  length found `seq` pure found

What the loop does with it:

  • The first frame calls useTaskStatus with a new key, which starts a worker thread.
  • Later frames return immediately. TaskRunning previous carries the last completed result, so the list does not flash empty when a new query starts.
  • The worker finishes and wakes the loop for a frame. The next call reports TaskDone.
  • Changing the key (typing a new committed query) cancels the old worker with an asynchronous exception and starts the new one.

useTask is the simpler variant when only the latest result matters:

contents <- useTask (appFile app) path (T.readFile (T.unpack path))
label (fromMaybe "Loading..." contents)

3. Retrying a failed job

A job that throws becomes TaskFailed err previous. The exception is shown and the key includes an attempt counter, so pressing Retry reruns the same input:

flakyCard :: App -> NanoUI ()
flakyCard app = do
  attemptVar <- useVar (0 :: Int)
  attempt <- readVar attemptVar
  -- Same input every time, so the attempt number is the key: bumping it is
  -- what reruns the job.
  status <- useTaskStatus (appFlaky app) attempt (flakyRequest attempt)
  -- Each branch declares different widgets, so the whole case is one scope.
  scope $ case status of
    TaskRunning _ -> rowWith (tight . gap 8 . alignMid) $ do
      spinner
      label "Contacting the server..."
    TaskDone reply -> rowWith (tight . gap 8 . alignMid) $ do
      label reply
      whenM (button "Run again") (modifyVar attemptVar (+ 1))
    TaskFailed err _ -> rowWith (tight . gap 8 . alignMid) $ do
      danger (T.pack (displayException err))
      whenM (button "Retry") (modifyVar attemptVar (+ 1))

Two rules are visible here:

  • The key must change to rerun. Keying by the input alone would never restart an identical request; the attempt number is part of the key.
  • Each branch is a whole scope. The branches declare different widgets; the scope keeps the widget ids after the card stable as the status changes.

Resource safety belongs inside the job. A file handle, a network connection, or a temporary directory should be acquired with bracket, because cancellation is an asynchronous exception:

withConnection connInfo $ \conn -> ...

4. Streams: many updates, one frame

A Stream is for work that pushes repeatedly: progress ticks, sensor readings, tokens from a model. The producer is a function that receives update and runs until it returns or is cancelled:

progressCard :: App -> NanoUI ()
progressCard app = do
  running <- useVar False
  checkbox "Run" running
  isRunning <- readVar running
  -- When "Run" is unticked 'useStream' is not called, and that alone kills
  -- the producer: there is no stop button to wire up. Ticking it again
  -- starts a fresh producer from the initial value. The scope keeps
  -- anything declared after it on stable ids.
  scope $ when isRunning $ do
    pct <- useStream (appProgress app) () (0 :: Int) $ \update ->
      forM_ [1 .. 100] $ \i -> do
        threadDelay 50000
        -- Each update wakes the loop for one frame; updates that arrive
        -- between frames share it.
        update (const i)
    progressBar (fromIntegral pct / 100)
    muted
      ( if pct >= 100
          then "Done. Untick and tick Run to start over."
          else T.pack (show pct) <> "%"
      )
  • Stopping is not calling the hook. When isRunning is false, useStream is not called, and the producer is cancelled. There is no stop button to wire up.
  • Updates coalesce. If the producer pushes five values between two frames, the next frame draws the latest one; it does not run five frames.
  • The stream’s state starts from the initial value. Restarting after a pause begins at 0 here, which is why the label explains how to start over. To resume from the last state, save it outside and pass it as the initial value (the live chart below does exactly that).
  • Keep the hook outside tabs when the stream must keep running. Like a task, a stream is released when its hook is skipped for a whole frame.

The frame loop sleeps until the next update. A paused progress pane costs no frames.

5. A live chart

The chart is a Stream feeding a PlotCache. The cache is allocated once and passed to plot; it compares the chart against the one it drew last time and rebuilds the diagram only when the data or theme changes:

data App = App
  { appFeed :: !(Stream () Feed)
  , appSaved :: !(Var Feed)
  , appPlots :: !PlotCache
  }

newApp :: IO App
newApp = App <$> newStream <*> newVar emptyFeed <*> newPlotCache

The view pauses by not calling the stream, and resumes from the saved feed:

view :: App -> NanoUI ()
view app = columnWith (padAll 16 . gap 12 . grow) $ do
  running <- useVar True
  isRunning <- readVar running
  saved <- readVar (appSaved app)
  -- While running, the stream is the source of truth; 'saved' only seeds a
  -- restarted producer and is ignored after its first frame. While paused,
  -- 'useStream' is not called and the saved samples are shown instead.
  feed <-
    scope $
      if isRunning
        then useStream (appFeed app) () saved $ \update -> forever $ do
          threadDelay 100000
          update advance
        else pure saved

  rowWith (tight . gap 8 . alignMid . fillW) $ do
    whenM (button (if isRunning then "Pause" else "Resume")) $ do
      when isRunning (writeVar (appSaved app) feed)
      writeVar running (not isRunning)
    muted
      (if isRunning then "Live: a sample every 100 ms" else "Paused: the loop is idle")

  let
    points = feedPoints feed
  -- A crosshair for reading values off the plot; the response reports the
  -- sample nearest the pointer.
  resp <-
    withCursorShape
      UiCursorCrosshair
      (plot (appPlots app) (fillW . minH 300) (walkChart points))

  rowWith (tight . gap 16 . alignMid . fillW) $ do
    let
      ys = fmap snd points
    -- Both parts come and go, so each sits in a scope.
    scope $
      if Seq.null ys
        then muted "Waiting for the first sample..."
        else do
          kv "min" (fmt (minimum ys))
          kv "max" (fmt (maximum ys))
          kv "last" (fmt (feedLevel feed))
    scope . for_ (plotHover resp) $ \hover ->
      kv
        "cursor"
        ( "#"
            <> T.pack (show (round (hoverDataX hover) :: Int))
            <> " = "
            <> fmt (hoverDataY hover)
        )

Feed, advance, and fmt are in LiveChart.hs; walkChart builds the chart value:

walkChart :: Seq (Double, Double) -> Chart
walkChart points =
  withGrid GridBoth
    . withLegend LegendNone
    . withXAxis "sample"
    . withYAxis "value" $
    chart [line "walk" points]

The chart API is small:

  • line, scatter, bar, area, and step build series from points (or category/value pairs for bars).
  • chart takes the list of series; withGrid, withLegend, withXAxis, withYAxis, and withTitle decorate it.
  • plot cache layout theChart draws it and returns a PlotResponse whose plotHover is the nearest data point under the pointer.

Building the Chart value every frame is fine: it is a plain value, and comparing a few hundred points is cheap. What is expensive is rebuilding the diagram; the PlotCache is what prevents that.

State & Var

The view runs every frame. Nothing is retained between frames except the state you keep explicitly, so the first design question in a nano-ui application is not “which widget?” but “where does this value live?”

Most state lives in a Var: a typed mutable reference. Input widgets take the Var they display and mutate it directly; there is no callback and no on-change handler.

counter :: NanoUI ()
counter = rowWith (gap 8 . alignMid) $ do
  n <- useVar (0 :: Int)
  whenM (button "-") (modifyVar n (subtract 1))
  label . T.pack . show =<< readVar n
  whenM (button "+") (modifyVar n (+ 1))

Keep state, derive values

A value that changes over time and cannot be recomputed belongs in a Var. A value that can be recomputed belongs in a local binding, computed fresh every frame:

appView :: App -> NanoUI ()
appView app = do
  -- Keep: the inputs to the next frame.
  draft <- useVar ""
  settings <- readVar app.appSettings

  -- Derive: computed from what was kept.
  label ("Signed in as " <> settings.nickname)
  label ("Draft: " <> T.pack (show (T.length draft)) <> " characters")

Keeping a derived value in a second Var means every place that changes the source must also update the copy. The first place that forgets is a bug.

Allocating state

There are two ways to create a Var, plus one for dynamic collections:

useVarnewVar

TypesInt, Float, Double, Bool, Text, SortCol (useEnumVar for any Bounded/Enum type)Any type

useVar needs no setup. Its initial value is used only when the slot is first created; call writeVar to reset it later. Its slots are counted separately from widget ids, but a conditional useVar still needs scope so later slots keep their positions:

showAdvanced <- useVar False
scope . whenM (readVar showAdvanced) $ do
  level <- useVar (3 :: Int)
  ...

newVar can hold any type. Allocate it once in IO and pass it into the view:

data App = App
  { appSettings :: Var Settings
  , appTodos :: Var [Todo]
  }

newApp :: IO App
newApp = App <$> newVar (Settings 40 False "Ada") <*> newVar []

main :: IO ()
main = do
  app <- newApp
  runSdlApp opts (appView app)

Passing the same Var to two widgets shares their state. Allocating a Var inside the view creates a fresh one on every pass.

For dynamic collections, VarMap gives one Var per key:

rows <- newVarMap

rowState <- varAt rows todoId (RowState False "")
retainVars (`elem` liveIds) rows

varAt returns the existing Var for a key or creates it. dropVar removes one; retainVars keep prunes everything whose key fails the predicate.

Projections and read-only views

A record in a Var gives a Var for each field. With Generic and OverloadedRecordDot:

data Settings = Settings
  { volume :: !Float
  , silent :: !Bool
  , nickname :: !Text
  }
  deriving (Eq, Generic)

settings <- newVar (Settings 40 False "Ada")

slider 0 100 settings.volume
checkbox "Silent" settings.silent
textInput settings.nickname

settings.volume is a Var Float projecting one field. Editing it does not repaint what reads only settings.nickname.

  • constVar x is read-only; writes are no-ops. Use it for a derived value shown in an input widget.
  • withValue val widget runs a Var widget against a temporary Var and returns the result and final value. nano-ui-emit uses it for emitChanged.
  • zoomVar getter setter projects a computed part of a larger Var; zoomVarL does the same from a lens.
  • Lists: forEachVar key list body gives per-element Vars that follow their keys across reorders. withElemVars is the variant for filtering or sorting yourself.

What a write costs

readVar records a dependency for the current pass. When the value changes, nano-ui classifies the write:

WriteWhenCost
ForwardWritten before any read this passOne pass; later reads see the new value
BackwardWritten after being read earlier this passA second view pass, with one-shot input events cleared
UnchangedNew value == old valueNo-op: no pass, no repaint

Two habits follow:

  • Place readVar below the widget that edits the value when the order is free. Typing then resolves in one pass; reading above it costs a second pass per change.
  • Do not readVar a value only to pass it back into the same widget. Passing the Var is enough.

Tip

When an input widget is bound to a Var and nothing in the view calls readVar on it, only that widget repaints on change. A readVar promotes the write to a full-window repaint.

peekVar reads without recording a dependency. readVarIO, writeVarIO, and modifyVarIO are the thread-safe versions; after a background write, call the callback from askWake to schedule a frame. Never touch the UI Context from a worker thread.

Lifetime and resources

Tasks, streams, image handles, drag handles, plot caches, and file-dialog ids are allocated in IO during setup and stored in the application record, exactly like a newVar:

data App = App
  { appDocument :: Var TextDocument
  , appTask :: Task Text [Text]
  }

A handle allocated inside the view is a per-frame leak. If the view needs a new handle when a key changes, allocate it in setup and key its use, or use a hook that owns its lifetime (useTask, useStream, useImageRgba).

Common mistakes

  • liftIO (newVar ...) inside a view allocates every pass; move it to setup.
  • A conditional useVar without scope shifts later slots.
  • Reading above the input that writes costs a second pass per change.
  • Writing a freshly computed NaN redraws forever (NaN /= NaN); guard the write.
  • A second Var holding a derived value drifts; compute it instead.

Widget Identity & Keys

Widget state (caret position, text selection, an open drop-down, a scroll offset, per-row local Vars) is stored under the widget’s id, not in the widget. Ids are generated deterministically from the call order among siblings. If the order changes, the state appears to jump to a different widget. This section explains how to keep the order stable.

How ids are assigned

Each container assigns ids to its children counting from zero. A column with three labels has children 0, 1, and 2; a nested row starts its own count. Ids are per container, not global.

Two separate id spaces exist:

  • Widget ids for layout nodes, focus, input state, and scroll state.
  • useVar slots, counted in call order, with their own counter and key space.

That separation means a conditional widget does not shift useVar slots, and a conditional useVar does not shift widget ids. Both still need their position kept stable if they come and go, which is what scope does.

Rule 1: keep the call order stable

The structure of the calls should be the same on every frame. Straight-line code and ordinary if/case over widget values are fine; conditionally calling a widget changes the count for everything after it.

Rule 2: wrap conditional subtrees in scope

scope reserves one slot whether or not its body runs, so later siblings keep their ids:

-- BAD: when showDetails is False, every later sibling shifts down one id.
when showDetails $ do
  label "Details..."
  textInput detailsVar

-- GOOD: one stable slot, whether or not the body runs.
scope $
  when showDetails $ do
    label "Details..."
    textInput detailsVar

The same applies to a branch that swaps two widgets:

scope $
  if isEditing
    then textInput draft
    else label (todoText todo)

scope is cheap and local. Use it around anything that may not run on every frame: a conditional block, a case whose branches declare different widgets, a placeholder that appears while loading. Overlays are the exception with a simpler rule: call them unconditionally (see Rule 4).

Rule 3: key dynamic lists with withKey

Never key a list item by its index. Wrap each item in withKey with a stable, sibling-unique key: an item id, a UUID, a file path.

column $ for_ items $ \todo ->
  withKey (todoId todo) $ do
    row $ do
      label (todoText todo)
      whenM (button "Delete") (deleteItem (todoId todo))

Without the key, removing the first row makes every later row inherit the previous row’s caret, selection, and local Vars. With it, the row’s state travels with the item through filters, sorts, and reorders.

withKey is also how per-row useVar calls stay attached to their row:

for_ items $ \todo ->
  withKey (todoId todo) $ do
    expanded <- useVar False      -- follows todoId, not the row index
    ...

The full todo-list tutorial builds this up step by step: Build a Todo List.

Lists that use Vars per element

For a list stored in a Var [a], forEachVar key list body gives each element a Var a and puts the body under the element’s key automatically. withElemVars does the same but passes the elements and an at accessor, for when you filter or sort the list yourself:

withElemVars todoId items $ \todos at ->
  forM_ (filter visible todos) $ \todo ->
    withKey (todoId todo) (row (at todo))

Rule 4: call overlays unconditionally

modal, window, and popup take a Var Bool for their open state and draw nothing while it is false. Call them every frame:

confirm <- useVar False
whenM (button "Delete...") (writeVar confirm True)

modal confirm "Delete the file?" $
  whenM (button "Delete") (deleteFile >> writeVar confirm False)

Wrapping the call in when (readVar confirm) shifts every later sibling’s id when the dialog opens and closes, which is exactly the jump scope and keys exist to prevent. For derived open state, pass constVar and use the primed variants.

Rule 5: retain state for dynamic collections

Widget and Var state under a key survives the key not being drawn for a while: hide a filtered row and show it again, and its draft is still there. That state is not freed automatically. For an unbounded collection (a chat log, a set of tabs, a streaming table), keep the per-row state in a VarMap and prune it periodically:

retainVars (`elem` liveIds) rowVars

Without pruning, a long-running application accumulates state for rows that no longer exist. With aggressive pruning, state disappears the moment a row is filtered out; choose the policy per collection. A todo row can keep its draft while hidden; a row from a 100,000-row log cannot.

Elm-Style State

nano-ui-emit is the reducer-based alternative to Var: instead of mutating state directly, the view emits typed messages, and a pure reducer folds them into a model.

data Model = Model {counter :: Int, name :: Text}
  deriving Eq

data Msg = Increment | Decrement | SetName Text

view :: Model -> NanoUIE Msg ()
view m = column $ do
  heading "Profile"
  row $ do
    emitWhen (button "-") Decrement
    label (T.pack (show m.counter))
    emitWhen (button "+") Increment
  emitChanged textInput m.name SetName

update :: Msg -> Model -> Model
update Increment m = m {counter = m.counter + 1}
update Decrement m = m {counter = m.counter - 1}
update (SetName n) m = m {name = n}

main :: IO ()
main = runSdlAppReduce defaultSdlOptions update (Model 0 "Ada") view

Widgets, layout, focus, and keys are unchanged. Only the state model differs.

Emitting

NanoUIE msg a is a UI action that can emit only msg. There is no Typeable constraint and no runtime type test: emitting the wrong type is a compile error.

A NanoUIE view is an ordinary NanoUI action with the view’s message sink in scope (an implicit parameter, ?emit). Every core widget runs in it unchanged, so NanoUI.Emit re-exports NanoUI and adds the functions below. An emit inside a container, an overlay body, a tab or a menu callback goes to the sink of the view around it.

FunctionEmits when
emit msgImmediately
emitWhen widget msgThe widget returns True (button click, submitted field)
emitChanged widget old toMsgA Var a -> NanoUI r widget’s final value differs from old

column $ do
  label "Settings"
  withKey "form" $ do
    emitChanged (slider 0 100) volume SetVolume
    emitWhen (button "Save") Save

emitChanged runs the widget against a temporary Var seeded with the model value and emits the new value only if it differs. emitEdited is its stricter form for text fields, where programmatic writes should not look like edits.

Give each view a signature in its own message type, view :: Model -> NanoUIE Msg (). The runners take a view of that shape, and a local helper defined outside a view needs the signature too, or GHC finds no sink for its emit.

Caution

Emit only inside an event branch. emit Save at the top level of a view emits on every pass, and the reducer runs every message. The adapters above already guard on the widget’s event.

Messages are collected across every pass of a frame, including local-Var rebuilds, and reduced at frame end in emission order.

Components

mapMessages embeds a child view whose message type is smaller than its parent’s:

data ChildMsg = ChildIncrement | ChildReset

data ParentMsg = Child ChildMsg | SaveAll

childView :: Int -> NanoUIE ChildMsg ()
childView n = row $ do
  emitWhen (button "+") ChildIncrement
  label (T.pack (show n))
  emitWhen (button "Reset") ChildReset

parentView :: Int -> NanoUIE ParentMsg ()
parentView n = column $ do
  mapMessages Child (childView n)
  emitWhen (button "Save All") SaveAll

Messages go straight to the parent’s sink in traversal order, with no intermediate queue. mapMessages changes the message type, not widget identity: a list still needs withKey around each component, exactly as a Var-based row does.

For local UI state, keep using Var inside the component; the durable model stays in NanoUIE.

Running and testing

runSdlAppReduce and runRgfwAppReduce take an update function, an initial model, and a view:

runSdlAppReduce defaultSdlOptions update initialModel view

The view runs with the current model, messages are reduced at frame end, and the drawing shown for that frame is from before the reduction. If the model changed, another frame is requested to draw it. That follow-up frame is intentional.

For tests and embedded uses:

Rules and pitfalls

  • Keep update pure. File and network I/O belong in the view’s event branch or in an effect queue interpreted outside the reducer.
  • Do not duplicate model state in Vars. Local UI state is fine; durable state should have one home.
  • Guard every emission. Unconditional emissions run on every pass.
  • Component keys are required in lists. Give each instance a distinct withKey.
  • Keyboard and focus rules are unchanged. Focus queries still belong at the end of the view.
  • Model changes draw on the next frame. Do not compensate by writing the model into a Var mid-frame.

The Var style is covered in State & Var; the frame consequences are in Architecture & Internals.

Scrolling

A scroll container needs a bounded viewport on its scrolling axis:

scrollWith (fixedH 300 . fillW) $
  column $ for_ items label

Without a bounded ancestor, grow can leave a scroller with nothing to size against.

  • scrollWith returns the body’s result.
  • scrollArea also returns the scroller’s WidgetId, for programmatic control.
  • scroll2DWith / scrollArea2D scroll both axes.
  • A scroller that fills both axes (grow) drops its well and paints the page background (pageBackground, themeWindow by default). Scope a view in styled panelPage for a page on the panel surface.

Virtualization

For 10,000+ rows, build only the visible slice and use spacers for the rest. Capture the scroller id and read the previous layout with getScrollMetricsUi:

virtualizedList :: [Item] -> NanoUI ()
virtualizedList items = do
  sid <- currentId
  scrollWith (fixedH 500 . fillW) $ do
    metrics <- getScrollMetricsUi sid
    let rowH = 28
        total = length items
        (offsetY, viewH) = case metrics of
          Nothing -> (0, 0)
          Just m  -> (v2Y (scrollOffset m), rectH (scrollViewport m))
        firstVisible = max 0 (floor (offsetY / rowH))
        lastVisible  = min total (firstVisible + ceiling (viewH / rowH) + 2)
        topH    = fromIntegral firstVisible * rowH
        bottomH = fromIntegral (total - lastVisible) * rowH
        visibleRows = take (lastVisible - firstVisible) (drop firstVisible items)
    columnWith (tight . fillW) $ do
      when (topH > 0) (spacer Fit (Fixed topH))
      for_ visibleRows $ \item ->
        withKey (itemId item) $
          labelWith (fixedH rowH . fillW) (itemTitle item)
      when (bottomH > 0) (spacer Fit (Fixed bottomH))

scrollViewport excludes padding and the scrollbar lane; use it, not the container rectangle, for the visible height. scrollOffset is the current offset. The metrics read registers a layout dependency, so a resize triggers another frame.

See packages/nano-ui-demo/examples/LongList.hs (100,000 rows) and Logs.hs (sticky-to-bottom).

Programmatic scrolling and wheel tuning

metrics <- getScrollMetricsUi sid
when shouldReveal $
  scrollRectIntoViewUi sid (Rect 0 (row * rowH) 1 rowH) ScrollNearest ScrollInstant

One wheel notch scrolls 60 logical pixels by default. For fixed-height rows, set the step so a notch is one row:

  {scrollWheelStep = rowHeight, scrollSmoothTime = 0}

Buttons

button   :: Text -> NanoUI Bool
button'  :: Text -> NanoUI Response
buttonWith :: (Layout -> Layout) -> Text -> NanoUI Bool
buttonContent :: NanoUI () -> NanoUI Bool
iconButton :: Svg -> Text -> NanoUI Bool

button returns True only on the frame it is activated, by left click or by Enter/Space while focused:

whenM (button "Save Document") (liftIO saveFile)

The whenM guard is essential: the view runs every frame, so an unguarded side effect would run forever.

Use the primed form when you need the response: hover state, a rectangle for an anchored popup, or a tooltip.

resp <- button' "Refresh"
tooltip resp "Poll the remote server for updates"
when (respClicked resp) refresh

buttonContent puts any view inside a button. The content is for display; a click anywhere on the button activates it:

whenM (buttonContent $ rowWith (gap 6 . alignMid) $ do
          svgIcon 16 saveIcon
          label "Save") $
  saveDocument

iconButton is the leading-icon case; an empty label gives an icon-only square button.

Menus

menuItem is a row that returns True when clicked. menuItemShortcut also displays a chord and binds it while the menu is open. menuSeparator and menuItemDisabled complete the row set.

A menu bar is a menuButton' plus a popup' anchored to its rectangle:

fileOpen <- useVar False
isOpen <- readVar fileOpen
btn <- menuButton' "File" isOpen
when (respClicked btn) (writeVar fileOpen (not isOpen))

let cfg = (defaultPopupConfig (AnchorRect (respRect btn)))
            {cfgPlacement = PlacementBelow, cfgOffset = 0}
(popupResp, _) <- popup' (constVar isOpen) cfg $
  columnWith (tight . gap 0) $ do
    whenM (menuItemShortcut "New" (cmdOrCtrl <> key 'n')) newDocument
    whenM (menuItem "Open...") openDocument
    menuSeparator
    whenM (menuItem "Exit") (writeVar fileOpen False >> quitUi)
when (respClicked popupResp) (writeVar fileOpen False)

constVar supplies a read-only open flag: the truth is the menu’s own state, and a click on the popup is written back to the real Var.

Important

Call overlays unconditionally. popup' draws nothing while closed, but wrapping it in when isOpen changes later widget ids each time the menu opens.

Bind a command chord outside the menu as well as on its row, so it works with the menu closed:

whenM (menuItemShortcut "Save" saveChord) saveDocument
whenM (shortcut saveChord) saveDocument

Only the first binding of a chord in a frame fires, so the open menu’s row wins. A complete menu bar is built in Build a Notepad.

contextMenu attaches a right-click menu to any widget with a Response:

(_, rowResp) <- mouseArea (fillW . gap 6) (label "Right-click for actions")
_ <- contextMenu rowResp $ do
  whenM (menuItem "Inspect") inspectRow
  whenM (menuItem "Copy") copyRow

Text Editing

nano-ui offers two levels of multi-line editing:

  1. textArea works on a Var Text. It is right for short notes, descriptions, and commit messages, where the whole string is the value.
  2. textAreaDocument works on a Var TextDocument. It is built for large files, editors, and code buffers, with line-level immutable sharing and an undo history that survives edits.

textArea for short text

notes <- useVar ""
textArea notes

Every edit produces a new Text; for a few kilobytes that is a fine trade for the simple API.

textAreaDocument for documents

editorView :: Var TextDocument -> NanoUI ()
editorView docVar = do
  resp <- textAreaDocumentWith' (grow . minW 320 . minH 200) docVar
  when (respChanged resp) markDirty
  writeVar editorId (respId resp)

Only the edited lines are copied; unchanged lines are shared. documentText materializes the whole text; call it when saving, not on every edit.

save = liftIO (BS.writeFile path (TE.encodeUtf8 (documentText doc)))

documentLineCount is cheap and is the right way to show a line count in a status bar.

One undo history

Keyboard edits, mouse selection, the right-click menu, and programmatic commands all dispatch TextCommands, so they share one undo history:

data TextCommand
  = InsertText Text
  | Delete TextMotion
  | Move TextMotion Bool
  | SelectAll
  | Select Cursor Cursor
  | Replace Cursor Cursor Text
  | ReplaceAll Text
  | Undo
  | Redo
  | Cut
  | Copy
  | Paste

Run a command against a field by its WidgetId:

whenM (menuItem "Undo") (runTextCommand editor Undo)
whenM (menuItem "Insert date") (runTextCommand editor (InsertText today))

Query history state for menu enablement:

editor <- readVar editorId
canUndo <- textCanUndo editor
canRedo <- textCanRedo editor

A complete Edit menu built this way is in Build a Notepad.

Tip

Directly overwriting the Var Text or Var TextDocument from outside resets the undo stack. To make a programmatic edit undoable, issue a TextCommand (InsertText, ReplaceAll, and so on) instead of writing the Var.

Reading the response

The primed variants return a Response:

  • respChanged reports an edit, not a caret move. Use it to mark a document dirty.
  • respSubmitted reports Enter in a single-line field.
  • respId identifies the editor for commands and focus.

For a single-line field, textInput and textInput' are the equivalents; searchInput' adds debounced change reporting and a clear button.

tab creates a plain header; closableTab adds a close button and reports the close through the primed response:

active <- useVar ("overview" :: Text)
resp <- tabs' active
  [ closableTab "overview" "Overview" overviewView
  , closableTab "logs" "Logs" logsView
  ]
for_ (tabClosed resp) closeTab
let activeKey = tabActive resp

The caller must remove the tab: tabs' reports tabClosed, it does not remove it. A key no tab has selects the first tab and writes that key back to the Var.

tabBar / tabBar' draw headers only and leave the body to the caller, which is useful for pane layouts and custom bodies. tabsConfigured / tabBarConfigured take a TabsConfig:

let cfg = defaultTabsConfig
      {tabsStyle = TabSegmented, tabsOrientation = TabTop, tabsTrailing = newTabButton}
tabsConfigured cfg active tabs

Tables

table renders Colonnade columns. Header clicks sort through a Var SortCol:

data Process = Process
  { pid :: Int
  , name :: Text
  , mem :: Int
  }

processTable :: [Process] -> Var SortCol -> NanoUI ()
processTable procs sortVar =
  table "procs" cols procs sortVar
  where
    cols = mconcat
      [ headed "PID" (\p -> label (T.pack (show (pid p))))
      , headed "Name" (\p -> label (name p))
      , headed "Memory (MB)" (\p -> label (T.pack (show (mem p))))
      ]

SortCol holds the active column and direction. simpleTable headers rows renders a table of text rows. table' returns a TableResponse with the updated sort, column order, and hidden columns; tableConfigured adds frozen rows/columns, fixed column widths, and hidden columns through TableConfig. Rows are virtualized internally.

Cell helpers: textCell, cellWidget, widgetCell, and Cell with an explicit sort key (cellKey). A cell with a widget view still needs cellText if its natural width should be measured.

Trees

items :: [TreeItem]
items =
  [ TreeItem "src" [TreeItem "Main.hs" [], TreeItem "Widgets" []]
  , TreeItem "README.md" []
  ]

fileTree :: [TreeItem] -> Var Int -> NanoUI ()
fileTree = tree "file-tree"

TreeItem is the library type (treeItemLabel, treeItemChildren), not an app-defined record. tree reports the selected pre-order index through the Var Int, not an item id. For large trees, keep the expansion set in a VarMap keyed by a stable path, and rebuild the visible items before calling tree.

Overlays & Windows

Overlays are modal dialogs, draggable floating windows, anchored popups, and hover tooltips. They are ordinary NanoUI actions called every frame, with a Var Bool for open state.

Call overlays unconditionally

modal  :: Var Bool -> Text -> NanoUI () -> NanoUI ()
window :: Var Bool -> Text -> NanoUI () -> NanoUI ()
popup  :: Var Bool -> PopupConfig -> NanoUI () -> NanoUI ()

Caution

Always call an overlay on every frame. Wrapping it in when isShown (modal ...) shifts widget ids for all subsequent siblings when it opens or closes, which moves focus, carets, and per-row state. Overlays draw nothing while their Var Bool is False.

showConfirm <- useVar False

whenM (button "Delete File...") (writeVar showConfirm True)

modal showConfirm "Confirm Deletion" $ do
  label "Are you sure you want to permanently delete this file?"
  row $ do
    whenM (button "Cancel") (writeVar showConfirm False)
    whenM (buttonWith destructive "Delete") $ do
      deleteFile
      writeVar showConfirm False

Escape, a click outside, and the close button write False to the Var, so the dialog closes in the same frame. A modal blocks interaction with the content behind it and is drawn above it.

Modals

modal renders a titled panel with a close button, centered in the window and limited to the window’s bounds. The body is not scrolled automatically; wrap it in scrollWith for long content, and give the panel a size with modalWith when the body needs to fill it:

modalWith (fixedWH 600 400) open "Settings" $
  columnWith (fillW . fillH) settingsBody

modal' returns (Response, Maybe a), where the response reports a close request as a click. Use it when the open flag is derived from other state: pass constVar so the overlay cannot write the derived value, and write the real flag from the response:

open <- useVar False
(resp, _) <- modal' (constVar open) "Important" $ do
  label "This dialog is shown while `open` is True."
  whenM (button "OK") (writeVar open False)
when (respClicked resp) (writeVar open False)

For a modal without a title bar or close button, use modalPanel / modalPanel'; the panel surface and backdrop remain, and Escape or an outside click still writes False.

Floating windows

window is a draggable, resizable in-app window with a scrolling body. Other windows and the page remain interactive outside its bounds:

inspectorOpen <- useVar False
window inspectorOpen "Inspector" $ do
  inspectorBody

window' returns the body result and a response. Use window for panels that should coexist with the main content; use modal when the user must answer before doing anything else.

Popups

popup is a floating panel placed by a PopupConfig:

filterOpen <- useVar False
filterR <- button' "Filter"
when (respClicked filterR) (modifyVar filterOpen not)

popup filterOpen (defaultPopupConfig (AnchorRect (respRect filterR))) $ do
  checkbox "Fruit" showFruit
  checkbox "Vegetables" showVeg

A press on the anchor is not “outside”, so the button that toggles the popup does not immediately reopen it.

Popup placement:

  • AnchorRect (respRect r) anchors to a widget; AnchorPoint pos anchors to a coordinate.
  • cfgPlacement chooses PlacementAuto, PlacementBelow, PlacementAbove, PlacementAtCursor, and the other placements.
  • cfgOffset is the gap from the anchor.
  • cfgDismissable = False disables Escape/outside-click closing; act on the response from popup' instead.

An anchored popup positions against the previous frame’s respRect, so warm a frame before relying on it in tests. For long popup bodies, cap the height with popupWith (maxH ...) and scroll the body.

Tooltips

Tooltips are stateless and attach to any widget with a Response:

save <- button' "Save"
tooltip save "Write the file to disk"

more <- button' "More"
tooltipConfigured defaultTooltipConfig
  {tooltipPlacement = PlacementAtCursor} more "Follows the pointer"

The default delay is half a second; TooltipConfig sets the delay and placement. withTooltip attaches a rich tooltip widget instead of text.

Overlay rules of thumb

  • One modal at a time. Opening a second modal is allowed, but nested modals close inner-first; side-by-side modals close in declaration order.
  • Keep the open flag in a Var at the level that owns the decision, not in a child that may not be drawn.
  • Read focus after the overlay call, not before it.
  • Do not nest a scrollArea, panel, or card inside a dialog body without stripping its chrome; see Double borders.
  • Confirm destructive actions in a modal, not a popup: a popup can be dismissed by a click outside, which is the wrong default for a destructive action.

Drag and Drop

nano-ui includes local drag-and-drop primitives via useDrag, useDrop, dropZone, and useReorder. Applications own the data and choose which target accepts a release gesture.

Drag Lifecycle with useDrag

Allocate a dragHandle <- newDrag once during component setup, then use it in the view:

headers <- tabBar' active documents
gesture <- useDrag dragHandle (tabHeaders headers)

useDrag tracks gesture coordinates and reports one of four phases:

  • DragStarted: Pointer exceeded the drag distance threshold.
  • Dragging: Pointer is actively moving while button is held.
  • DragReleased: User released the mouse button over a target.
  • DragCancelled: Gesture cancelled via Escape key or lost focus.

Reordering Tab Strips

case gesture of
  Just d | dragPhase d /= DragCancelled -> do
    let remaining = filter ((/= dragPayload d) . fst) (tabHeaders headers)
        slot = insertionIndex DragAxisX (tabStripRect headers)
                 (map (respRect . snd) remaining) (dragAt d)
    case slot of
      Just i | dragPhase d == DragReleased -> moveTab (dragPayload d) i
      _ -> pure ()
  _ -> pure ()

insertionIndex returns Nothing outside the strip bounds and calculates the target insertion index respecting ancestor clips.

Pane Grids (paneGrid)

Dockable, splittable multi-pane arrangements (as seen in IDEs and profiling debuggers):

grid <- paneGrid cfg
case (gesture, pgrDropTarget grid) of
  (Just d, Just target)
    | dragPhase d == DragReleased -> do
        commitPaneDrop target
  _ -> pure ()

The destination provides pgdLocation (BesidePane paneId edge or OutsideGrid edge), pgdRect, and pgdPane for custom drop validation.

Custom Drawing & Controls

When the built-in widgets do not fit, draw the control yourself with the 2D canvas API.

The widgets in NanoUI.Widgets.Custom (knob, toggleSwitch, circularProgress, progressBar, spinner, sparkline) are designed to serve as reference implementations for custom widgets users may want to implement themselves. This API is meant to accompany the canvas API, demonstrating how 2D vector drawing, layout sizing, gesture hooks (useDrag2DOn, useWheelDeltaOn), keyboard navigation, and responsive state binding (bindVar) integrate into cohesive, interactive controls.

Reference custom controls

import NanoUI.Widgets.Custom
ControlSignatureDefault sizeNotes

toggleSwitchVar Bool -> NanoUI ()44×24Click, Space, or Enter toggles

Each has a primed form returning Response (knob', toggleSwitch', …) and a ...With form that takes a layout modifier and size parameters:

knobWith alignMid 48 0 100 volume
progressBarWith fillW 6 progress
sparklineWith (fixedWH 120 32) 120 32 samples

A settings row:

settingsRow :: Var Bool -> Var Float -> NanoUI ()
settingsRow enabled volume = rowWith (gap 12 . alignMid) $ do
  toggleSwitch enabled
  labelWith (alignMid . fixedW 64) "Enabled"
  knob 0 100 volume
  v <- readVar volume
  labelWith (alignMid . fontMono . fixedW 48) (T.pack (show (round v :: Int)))

The fixedW on the changing number keeps the controls from shifting. Read the value below the knob so a drag resolves in one pass.

spinner calls keepAnimating internally while it is drawn. Do not add a global keepAnimating; that would keep the loop running when the spinner is not visible.

Implementing custom controls

You can inspect the source code of NanoUI.Widgets.Custom as a blueprint for implementing your own controls. A typical interactive control follows this pattern:

  1. Allocate widget identity: (wid, ctx) <- freshWidget obtains a unique WidgetId.
  2. Define geometry & drawing: Specify layout constraints and vector draw ops via CustomWidgetSpec and runCanvasFor.
  3. Capture gestures & input: Use gesture hooks (drag <- useDrag2DOn resp, (_, scrollY) <- useWheelDeltaOn resp, nav <- useKeyNav wid) to compute value deltas.
  4. Synchronize state: Apply bindVar or finishInput to bind the pure calculation to the caller’s mutable Var.

Canvas drawing

customWidget (a CustomWidgetSpec with layout, draw, cursor, and content key) or canvas / canvasConfigured draws with the 2D canvas API:

import NanoUI.Path qualified as P

badge :: NanoUI ()
badge = canvas (fixedWH 120 40) $ \_rect -> do
  drawRoundedRect (Rect 0 0 120 40) 8 (colorRGBA 37 99 235 255)
  drawStrokePath (P.circle (V2 20 20) 8) 2 colorWhite
  drawText (V2 68 20) AlignCenter AlignMiddle "Ready" colorWhite

Outside a canvas, use customWidget with a CustomWidgetSpec:

(resp, ()) <- customWidget defaultCustomWidgetSpec
  { widgetLayout = fixedWH 48 48
  , widgetContent = contentKey [angle, volume]
  , widgetDraw = \cdc (Rect x y w h) -> runCanvasFor cdc $ do
      drawCircle (V2 (x + w / 2) (y + h / 2)) 16 (themeAccent (cdcTheme cdc))
  , widgetCursor = Just (\_ _ _ -> UiCursorPointer)
  }

runCanvasFor adapts tessellation to the display scale inside widgetDraw. drawContext / cdcTheme supply the active theme, font, hover, and press state.

Paths, strokes, and text

  • P.moveTo, P.lineTo, P.cubicTo, P.arc, P.circle build paths.
  • drawPath / drawPathWith fill them; P.NonZero or P.EvenOdd selects the fill rule, P.Solid or P.Linear the paint.
  • drawStrokePathWith takes a P.Stroke record (width, caps, joins, dash).
  • withTransform (translate/rotate/scale) and withClip scope drawing.
  • drawText pos alignX alignY txt color; measure with lineWidth and uiFontMetrics.
  • drawRoundedRect and drawStrokeRoundedRect draw a bordered box; the stroke is inset inside the bounds, unlike a centred path stroke.

Content keys and caching

Without widgetContent, a custom widget’s draw ops are rebuilt and diffed every frame. With a key, unchanged frames skip rebuild and repaint, but the key must cover everything the drawing reads:

(resp, ()) <- customWidget defaultCustomWidgetSpec
  { widgetLayout = fixedWH 48 48
  , widgetContent = contentKey [angle, volume, fromIntegral (round scrollY)]
  , widgetDraw = \cdc rect -> runCanvasFor cdc (drawGauge rect)
  }

A key that misses an input shows stale pixels. See Styling Gotchas.

A drawing whose layout rectangle never changes (a drag ghost pinned under the pointer with pinAt) gets no layout change when it moves. Give it an explicit version that includes what moves it:

-- dragGhostOps :: Rect -> SmallArray DrawOp
drawingVersioned (contentKey [mx, my]) (fixedWH 32 32) dragGhostOps

Otherwise it keeps the ops of the frame it first appeared in.

SVG & Vector Graphics

nano-ui includes vector SVG support at both the widget level and the canvas drawing level:

  • SVG icons: Parse in-memory SVG strings (parseSvg) or load SVG files (loadSvg), then display them with svgIcon or in buttons.
  • Canvas SVG textures: Rasterize SVGs to RGBA buffers with rasterizeSvg from NanoUI.Svg and draw them onto a canvas using drawImage.
  • Canvas to SVG export: Export DrawOp sequences directly to SVG vector files using nano-ui-svg (drawOpsToSvg).

1. SVG Icons in Views

Monochrome SVG icons use currentColor and automatically inherit the active text color. This means they can be tinted with fontColor or semantic styles:

import qualified Data.ByteString.Char8 as BS8
import NanoUI

-- Parse an inline SVG icon (e.g. 24x24 viewBox)
starIcon :: Svg
starIcon = case parseSvg "<svg xmlns='http://www.w3.org/2000/svg' viewBox='0 0 24 24'><polygon points='12,2 15,9 22,9.5 16.5,14.5 18.5,21.5 12,17.5 5.5,21.5 7.5,14.5 2,9.5 9,9'/></svg>" of
  Right svg -> svg
  Left err  -> error ("Invalid SVG: " ++ err)

-- Render SVG icons with various sizes and theme colors
iconBar :: Svg -> NanoUI ()
iconBar icon = rowWith (gap 12 . alignMid) $ do
  theme <- uiTheme

  -- 1. Standard icon sizing (24x24 logical pixels)
  svgIcon 24 icon

  -- 2. Scoped styling and tinting via fontColor
  svgIconWith (fixedWH 32 32 . fontColor (themeAccent theme)) icon

  -- 3. In an icon button
  whenM (iconButton icon "Star") $
    putStrLn "Starred!"

  -- 4. Custom button content
  whenM (buttonContent $ rowWith (gap 6 . alignMid) $ do
            svgIcon 16 icon
            label "Favorite") $
    putStrLn "Favorited!"

Multi-color SVGs preserve their embedded fill and stroke colors. For flexible image-style scaling, svgIconConfigured accepts ImageConfig with CSS-like fitting (FitContain, FitCover, FitFill).

2. Drawing SVG inside Canvas

Within CanvasM, you can draw rasterized textures with drawImage / drawImageUV / drawImageWith. To draw an Svg onto a canvas, rasterize it to RGBA bytes using rasterizeSvg (or rasterizeSvgIn) from NanoUI.Svg:

import NanoUI
import NanoUI.Svg (rasterizeSvg)
import NanoUI.Widgets.Custom (CanvasM, canvas, drawImage, drawRoundedRect, drawStrokeRoundedRect, drawText)

-- | A custom badge widget that draws an SVG icon alongside custom vector geometry.
customBadge :: ImageHandle () -> Svg -> Text -> NanoUI ()
customBadge imgHandle svg title = do
  theme <- uiTheme
  let iconPx = 32
      -- Rasterize the SVG to RGBA at target pixel dimensions with a tint color
      rgba = rasterizeSvg iconPx iconPx (themeAccent theme) svg

  -- Lease the rasterized texture in the backend atlas
  mIid <- useImageRgba imgHandle () iconPx iconPx rgba

  canvas (fixedWH 140 44) $ \(Rect x y w h) -> do
    -- Draw container geometry
    drawRoundedRect (Rect x y w h) 8 (styleBg (themeButton theme))
    drawStrokeRoundedRect (Rect x y w h) 8 1 (styleBorder (themeButton theme))

    -- Draw the rasterized SVG icon if registered
    case mIid of
      Just iid -> drawImage (Rect (x + 8) (y + 6) 32 32) iid
      Nothing  -> pure ()

    -- Draw accompanying text
    drawText (V2 (x + 48) (y + 22)) AlignStart AlignMiddle title (styleFg (themeButton theme))

3. Exporting Canvas Drawings to SVG (nano-ui-svg)

When you need vector screenshots, reports, or test fixtures, nano-ui-svg can export any DrawOp array generated by runCanvas or runCanvasFor directly to an SVG string:

import qualified Data.Text.IO as TIO
import NanoUI
import NanoUI.Draw.Svg (defaultSvgConfig, drawOpsToSvg, renderDrawOpsSvg, SvgConfig (..))
import NanoUI.Path qualified as P
import NanoUI.Widgets.Custom

-- | Draw a vector gauge and export it to an SVG file.
exportGaugeSvg :: FilePath -> Float -> IO ()
exportGaugeSvg filePath value = do
  let bounds = Rect 0 0 160 50
      ops = runCanvas bounds $ do
        -- Outer background
        drawRoundedRect bounds 10 (colorRGBA 30 41 59 255)
        drawStrokeRoundedRect bounds 10 1.5 (colorRGBA 56 189 248 255)

        -- Progress bar path
        let barW = 140 * clamp 0 1 value
        drawRoundedRect (Rect 10 32 barW 8) 4 (colorRGBA 56 189 248 255)

        -- Indicator circle & text
        drawStrokePath (P.circle (V2 24 18) 8) 2 colorWhite
        drawText (V2 42 18) AlignStart AlignMiddle "CPU Load" colorWhite

  -- Export directly as a standalone SVG document:
  TIO.writeFile filePath (drawOpsToSvg bounds ops)

To embed the output inside an existing HTML/SVG document, pass svgStandalone = False:

-- Emits an inner <g> fragment instead of a full <svg> document
let fragment = renderDrawOpsSvg defaultSvgConfig { svgStandalone = False } bounds ops

For whole-window or view-level SVG captures, see NanoUI.Draw.FrameSvg in nano-ui-svg.

Styling & Theming

Styling in nano-ui is scoped: a Theme holds a Style per surface kind, and styled/themed modify that theme for a subtree. There is no per-widget CSS and no global mutable stylesheet.

For a live tour of the modifiers, see the Interactive Styling Lab. For non-obvious behavior, see Styling Gotchas.

The theme’s five surfaces

FieldUsed by
themeButtonButtons, toggles, dropdown triggers
themeInputText fields, search boxes, numeric inputs, sliders
themePanelCards, containers, sidebars, toolbars
themePopupDropdowns, context menus, select popouts
themeFloatingWindowModals, floating windows, inspectors

A Style is bg, fg, border, borderWidth, cornerRadius, hoverBg, and activeBg. A Theme also defines semantic colors: themeAccent / themeOnAccent, themeMuted, themeSelection, themeFocusRing, themeWindow, themeSeparator, and the success/warning/danger tones.

The page behind the view is pageBackground: themeWindow by default, unless the theme sets themePage. panelPage gives a view that draws no panel the panel surface, so the app sits on the panel colour while themeWindow stays the window background behind it; pageColor sets any other page. The page is laid over the window background, so the window shows in the gaps between a page’s panels:

-- An app with no panel of its own: the panel surface is the page.
sdlAppTheme = Just (panelPage defaultTheme)

-- Or scope it to a page with no panels.
styled panelPage (columnWith (padAll 12) (label "Body"))

A full-window scroller (scrollWith grow) fills the page colour.

Built-in themes: defaultTheme (dark), defaultLightTheme, the Tomorrow variants, and themeFromBase16 / themeFromBase16Dark / themeFromBase16Light. Set one at startup with sdlAppTheme = Just appTheme, switch per frame with setUiTheme, or follow the OS with followSystemTheme / lightDark.

Scoped styling

-- Replace the base theme for a subtree.
themed defaultLightTheme mainContent

-- Modify the active theme for a subtree.
styled (primary . rounded 999) $ button "Continue"

Modifiers compose with (.); nested scopes inherit the outer modification. Theme scopes affect painting only, never layout metrics.

Useful modifiers:

  • Style fields: background, foreground, borderColor, borderWidth, borderSides, cornerRadius, hoverBackground, pressBackground, fillColor.
  • Theme-level: buttonStyle, inputStyle, panelStyle, everyStyle, accentColor, textColor, rounded, subtle, tinted, readableOn.
  • Semantic shortcuts: primary, destructive, success, warning, tone Danger, toneColor Warning.

A common local helper is a quiet button:

quiet = subtle . buttonStyle (foreground muted)

whenM (styled quiet (button "Skip")) skip

For a fully custom look, define a palette record, build a Theme from it, and derive scoped helpers. Keep three surface levels (well, shelf, controls) and reserve color for meaning.

Interaction states

Widgets move through four states:

  1. Default: styleBg, styleFg, styleBorder.
  2. Hover: styleHoverBg.
  3. Pressed: styleActiveBg, while the primary button is held inside the widget.
  4. Disabled: dimmed and non-interactive.

disabledWhen cond subtree disables interaction and dims rendering while preserving layout and state:

disabledWhen isSaving $ row $ do
  button "Cancel"
  button "Confirm"

Shortcuts and pointer events inside a disabled subtree are suppressed automatically.

Keyboard, Focus & IME

Keyboard input is read during the frame, not registered with the window. A focused widget claims the keys it uses; shortcuts and key listeners are filtered automatically.

Shortcuts

import NanoUI.Shortcut

saveChord = cmdOrCtrl <> key 's'

saveCommand = whenM (shortcut saveChord) saveDocument

<> unions modifiers and keeps the right-hand key. key accepts a Key or a Char; letters are case-insensitive, and space maps to KeySpace:

ctrl <> key 's'                 -- Ctrl+S
cmdOrCtrl <> shift <> key 'p'   -- Cmd+Shift+P on macOS, Ctrl+Shift+P elsewhere
alt <> key KeyEnter             -- Alt+Enter
key (KeyF 5)                    -- F5

Use cmdOrCtrl for application commands. ctrl, shift, alt, and super are exact: ctrl <> key 's' does not match Ctrl+Shift+S.

  • shortcut fires on the frame the chord goes down, including auto-repeat (holding Ctrl+Z repeats undo).
  • shortcutOnce ignores auto-repeat. Use it for toggles and one-shot commands.

Only the first matching shortcut call in a frame fires. It consumes that key’s presses for the frame, so two bindings of the same chord never both run. Declaration order is priority order.

What suppresses a shortcut

A chord does not fire:

  • behind an open modal;
  • inside disabledWhen True;
  • when the focused widget claims the key: a text field keeps typing, cursor, and editing chords such as Ctrl+A and Ctrl+Z; buttons keep Enter and Space; sliders, selects, and lists keep arrows, Home, End, Page Up, and Page Down;
  • for Escape when takeEscape fails, or when an open overlay takes it first.

Focused widgets claim only their own unmodified or Shift-modified keys, so modified chords such as Ctrl+Enter, Alt+Left, or Ctrl+S still reach the application while a field is focused. The matching low-level functions are filtered the same way: keyPressed, keyPressedOnce, keyReleased, and keyHeld. Use raw pressedIn only when implementing a custom widget.

Menus and shortcuts

menuItemShortcut shows a chord beside a menu row and binds it while the menu is open. Bind the same chord outside the menu for when it is closed:

whenM (menuItemShortcut "Save" saveChord) saveDocument
whenM (shortcut saveChord) saveDocument

The open menu’s row is declared first, so it wins. Define the action once and connect both triggers to it.

Escape

Text fields do not claim Escape, so Escape can still close a popup, clear a selection, or leave a mode while the caret is in a field. That also means every Escape handler needs its own condition. Do not share the “a field is editing” guard used for Ctrl+A or Delete.

takeEscape claims a press for the current handler:

when isEditing (whenM takeEscape (writeVar editing False))
whenM takeEscape clearFocus

The first call that succeeds wins. An open popup, dropdown, or text-edit menu reserves Escape before the view sees it.

User-configurable chords

parseShortcut reads a chord from text, for a settings file or keymap editor:

case parseShortcut "C-S-s" of
  Right chord -> ...
  Left err    -> showError err

The syntax is modifier prefixes followed by a key: C- Ctrl, S- Shift, A- Alt/Option, s- Super, M- Command on macOS and Ctrl elsewhere. A key is one character as typed without Shift, or a named key in angle brackets: C-s, M-S-p, A-<Enter>, <F5>, C--, C-S-=. Name a symbol by its unshifted key, so Ctrl++ on a US layout is C-S-=.

shortcutLabel renders a chord for menus and tooltips.

Focus

  • Click a text field, select, slider, or focusable custom widget to focus it. Clicking elsewhere unfocuses the current field.
  • Tab moves to the next focusable widget; Shift+Tab to the previous.
  • requestFocus (respId resp) focuses a widget. focusNext / focusPrevious behave like Tab. clearFocus drops focus at the end of the frame.
  • holdFocus wid claims focus every frame for a view that handles input itself; it also consumes Tab so an editor can indent with it.

Focus requests are applied at the end of the frame, against that frame’s layout. A focus move is visible on the next frame:

resp <- searchInput' "Find" query
whenM (shortcut (cmdOrCtrl <> key 'f')) (requestFocus (respId resp))
-- next frame: the focus ring is drawn and isFocused answers True

A request can name a widget declared later in the same pass (for example with currentId just before it), but not one that is not declared on this pass at all. A widget that appears after a state change needs a delayed request:

editing <- useVar False
focusPending <- useVar False

showField <- readVar editing
scope $
  if showField
    then do
      fieldR <- textInput' draft
      whenM (readVar focusPending) $ do
        requestFocus (respId fieldR)
        writeVar focusPending False
    else label "Not editing"

whenM (button "Edit") $ do
  writeVar editing True
  writeVar focusPending True

Warning

Query focus at the end of the view. The node arena is reset before the view runs, so isFocused at the top always answers False. Keyboard shortcuts that depend on focus belong after the widgets have run.

A focus request is ignored for a disabled widget, a widget behind an open modal, one not declared this pass, or a group response that is not itself a Tab stop. A widget in an inactive tab is not declared, so it cannot keep focus; request focus again when the tab is shown.

disabledWhen dims a subtree and blocks interaction without changing layout or state. The focus ring is themed by themeFocusRing.

IME

Input method editors compose text before committing it. Built-in text fields handle the whole cycle, including caret rendering and suppressing shortcuts mid-composition.

A custom widget that reads committed characters from inputChars must opt in every frame it accepts text:

preedit <- useInputMethod wid InputNormal caretRect
for_ preedit drawCompositionAtCaret

useInputMethod :: WidgetId -> InputPurpose -> Rect -> NanoUI (Maybe Composition) places the candidate window at the caret and returns the in-progress composition to draw. Pass the caret rectangle, not the whole widget. It checks focus itself, so a separate isFocused guard is unnecessary.

Raw input fields: inputChars (committed text), inputKeys (pressed, including repeats), inputKeysNew (initial presses), inputKeysHeld, inputKeysReleased, and inputComposition. The terminal demo in packages/nano-ui-demo/examples/Terminal.hs is a complete custom text widget.

Testing

Focus changes apply on the next frame, so drive at least two frames:

ctx <- newContext
(_, _, _) <- runFrame ctx input1 view
(_, _, _) <- runFrame ctx input2 view

Warm up with warmup2 before targeting a widget by respRect. For shortcut tests, build input with keyInp / chordInp from NanoUI.Testing.Harness.

Async Work & Animation

The view must never block, and it should not redraw when nothing is moving. nano-ui handles both with the same idea: work is scheduled on a worker or a timed wake, and the frame loop sleeps until there is something to draw.

Compile with -threaded; the loop sleeps while a job runs and the job runs on a Haskell thread while it is blocked.

Task: one job per key

Allocate the handle once in IO:

data App = App
  { appSearch :: Task Text [Text]
  , appFlaky  :: Task Int Text
  }

newApp :: IO App
newApp = App <$> newTask <*> newTask

Use it from the view:

status <- useTaskStatus (appSearch app) queryKey (fetchSearchResults queryKey)

case status of
  TaskRunning previous -> showPreviousOrSpinner previous
  TaskDone results     -> renderResults results
  TaskFailed err prev  -> showError (displayException err)

useTask is the simpler form when only the latest result matters:

contents <- useTask (appFile app) path (T.readFile (T.unpack path))
label (fromMaybe "Loading..." contents)

Rules:

  • The key identifies the job. A new key starts a worker and cancels the old job with an asynchronous exception.
  • A skipped hook cancels the job. If the view does not call useTask for a full frame, because the pane is in an inactive tab or inside a branch, the work is released. Keep the hook outside tabs when work must continue while hidden.
  • To retrigger the same input, put a counter in the key. A Retry button must change the key or the job never reruns.
  • Cancellation is an async exception. Use bracket or withFile inside the job so resources are released when the user changes the query.
  • The result is forced on the worker. Return a value in weak head normal form; force a list’s spine with length found \seq` pure found`.
  • TaskRunning previous carries the last result, so a list does not flash empty while the next query runs.

Stream: repeated pushes

A Stream is for sensors, downloads, token streams, and anything that pushes repeatedly:

data App = App {appProgress :: Stream () Int}

newApp = App <$> newStream

pct <- useStream (appProgress app) () (0 :: Int) $ \update ->
  forM_ [1 .. 100] $ \i -> do
    threadDelay 50000
    update (const i)
progressBar (fromIntegral pct / 100)

The producer receives update :: (s -> s) -> IO () and returns when done, cancelled, or throwing. Each update wakes the loop; updates between frames coalesce into one frame.

  • Stop by not calling the hook. when isRunning (useStream ...) releases the producer.
  • Stopping discards the accumulated state. Save it outside and pass it as the next initial value to resume.
  • Producers must not touch the UI. They may call update from their thread or threads they start; never touch the UI Context.

Threads outside those handles

wake <- askWake        -- in the view, once

forkIO $ do
  result <- expensiveQuery
  writeVarIO queryResult result
  wake                 -- schedule one frame

readVarIO, writeVarIO, and modifyVarIO are the thread-safe Var operations. The wake repaints the whole window because nothing says which widget changed; fine for occasional updates, not for a per-token stream.

Animation

animateTo moves a value toward a target:

currentWidth <- animateTo (Tween EaseOutQuad 0.25 0) targetWidth

A Transition is either:

  • Tween ease duration delay, in seconds. EaseOutQuad, EaseInOutCubic, EaseOutBack, and EaseCubicBezier are some available curves.
  • Spring params, a damped spring. presetSmooth, presetBouncy, and presetStiff are the presets.
pos <- animateToA (Spring presetSmooth) (V2 targetX targetY)

Springs retarget mid-flight from their current position and velocity. animateToA animates any Animatable value (Float, Double, V2, or Color) channel by channel.

Continuous animation

pulse returns a value oscillating in [0, 1] with the given period in seconds:

opacity <- pulse 1.2

Clock-driven values do not, by themselves, keep the loop awake. A widget that draws from them must call keepAnimating with its own response, every frame it is on screen:

(resp, ()) <- customWidget defaultCustomWidgetSpec
  { widgetLayout = fixedWH 24 24
  , widgetContent = contentKey [t * 100]
  , widgetDraw = \cdc (Rect x y w h) -> runCanvasFor cdc $
      drawCircle (V2 (x + w / 2) (y + h / 2)) (6 + 3 * t) (themeAccent (cdcTheme cdc))
  }
keepAnimating resp

The loop goes back to sleep on the first frame that leaves it out.

Caution

Never force continuous redraws by dirtying the context every frame. That is an unpaced busy loop. Call keepAnimating only in the widget that is actually moving.

Timers

wakeAfter requests one frame after a delay in seconds:

clock = do
  label =<< currentTimeText
  wakeAfter 1

Call it on every frame that still needs the future wake; pending wakes reset each frame. Use wakeAfter for clocks, debounces, and polling on a schedule; use keepAnimating for continuous motion.

Window Chrome & Screenshots

nano-ui exposes window management at two levels: declarative settings and view actions from the core library, and SDL-specific chrome and screenshot helpers from nano-ui-sdl.

Window settings

Configure startup properties in WindowSettings:

opts =
  defaultSdlOptions
    { sdlWindowSettings =
        defaultWindowSettings
          { wsTitle       = "Main Window"
          , wsSize        = Size 1280 800
          , wsMinSize     = Just (Size 640 480)
          , wsMode        = Windowed      -- Windowed | Fullscreen | Hidden
          , wsTransparent = False
          , wsResizable   = True
          }
    }

Sizes are logical units, not pixels; the backend applies DPI scaling. wsPosition defaults to the desktop’s placement. wsOpacity (SDL) sets whole-window opacity.

Declarative and imperative actions

Inside the view:

  • Declarative setters (setWindowTitleUi, setWindowModeUi, setWindowMinSizeUi, setWindowMaxSizeUi, setWindowOpacityUi, setWindowIconUi) are no-ops when the value has not changed, so calling them every frame is safe and cheap:

    setWindowTitleUi (docName <> " - My App")

  • Imperative actions (moveWindowUi, centerWindowUi, resizeWindowUi, minimizeWindowUi, maximizeWindowUi, restoreWindowUi, toggleMaximizedUi) run on every call. Always guard them behind an event:

    whenM (button "Maximize") toggleMaximizedUi

quitUi ends the session; there is no separate “close window” command.

Close requests

By default the window closes as soon as the platform asks it to. To confirm unsaved work, set wsExitOnCloseRequest = False and handle the request in the view:

runSdlApp
  defaultSdlOptions
    { sdlWindowSettings = defaultWindowSettings {wsExitOnCloseRequest = False} }
  appView

appView = do
  ...
  whenM (winCloseRequested <$> askWindow) askBeforeQuitting

askWindow reports the window’s current state, including size, scale, maximized/fullscreen flags, and the close request. Build a Notepad wires this to a confirmation modal.

Custom title bars

For a frameless window (VS Code style, or ned), set the decorations and draw the bar yourself. The nano-ui-sdl backend supplies windowCaption, which draws the minimize/maximize/close buttons, registers the drag region, and reports a close click:

opts = defaultSdlOptions
  { sdlWindowDecorations = DecorationsNone
  , sdlWindowSettings = defaultWindowSettings {wsSize = Size 1000 720}
  }

appView :: NanoUI ()
appView = columnWith (fillW . fillH) $ do
  titleBar
  mainContent

titleBar :: NanoUI ()
titleBar = rowWith (fixedH 32 . fillW . alignMid) $ do
  menuResp <- button' "File"          -- interactive: exclude from dragging
  label "My Application"
  spacer
  closeClicked <- windowCaption [respRect menuResp]
  when closeClicked quitUi

windowCaption takes the rectangles of interactive widgets in the bar (menu buttons, tabs, search fields); the spans between them become draggable. The returned Bool is true on the frame the close button is clicked. windowCaptionWith customizes the buttons and resize border.

DecorationsFrame keeps the platform’s resize frame while removing the title bar; DecorationsNone removes both. On a resizable frameless window, edge resizing takes precedence over the drag region along the outer edges.

An optional rounded border around the whole view comes from windowFrame:

mainView = windowFrame (defaultWindowFrame (colorRGBA 70 70 80 255)) $ do
  ...

It draws a border and insets the view; the border does not consume layout space.

Screenshots

requestScreenshot asks the backend for the next presented frame and delivers it to a callback:

whenM (button "Screenshot") $
  requestScreenshot $ \maybeScreenshot -> ...

The callback runs in IO after the frame is presented. Keep it short (an IORef write or a forkIO for encoding); the next frame waits on it. Each request is answered exactly once, including with Nothing when the backend cannot capture.

For thread-safe capture use askScreenshot, which returns an IO action for a background thread, or useScreenshot for a per-key screenshot owned by a task:

data App = App
  { appShots :: Task Int (Maybe Screenshot)
  , appCount :: Var Int
  }

newApp = App <$> newTask <*> newVar 0

view app = do
  whenM (button "Screenshot") (modifyVar (appCount app) (+ 1))
  key <- readVar (appCount app)
  shot <- if key == 0 then pure Nothing else useScreenshot (appShots app) key
  for_ shot $ \(Screenshot pixels scale) -> ...

The nano-ui-sdl backend also has saveScreenshot env path (a BMP of the current frame) and captureScreenshot env (pixels), both on the display thread. For PNG encoding, use JuicyPixels or a similar library in a background thread.

Testing window behavior

Window operations are no-ops without a session, which makes headless tests possible: setWindowTitleUi and the other declarative setters can be called from NanoUI.Testing frames, and askWindow reports a default state. Native screenshot and chrome tests need a real SDL session, as in nano-ui-demo’s hidden-window self-tests.

import NanoUI
import NanoUI.Plot

  void $ plot (appPlots app) (fillW . fixedH 220) $

Validated forms

nano-ui-form builds applicative forms on ditto. A Form Text a has Text errors and returns a:

data Signup = Signup Text Text

signup :: Form Text Signup
signup =
  Signup
    <$> withFieldErrors (inputText "Name" "" `prove` notEmpty "Name is required")
    <*> withFieldErrors (inputText "Email" "" `prove` validEmail (const "Not an email address"))

Allocate owner <- newFormState once, then run it with a stable prefix:

submitted <- nanoFormSubmit owner "signup" "Sign up" signup
case submitted of
  Just (Signup name _) -> label ("Welcome, " <> name)
  Nothing              -> pure ()

nanoFormLive returns Just a whenever the form is valid; nanoFormEx takes a FormConfig; runNanoForm returns the view and result separately. Inputs include inputText, inputPassword, inputTextArea, inputCheckbox, inputSlider, inputSelect, inputRadio, and inputColor. Validation includes notEmpty, minLength, maxLength, inRange, validEmail, matches, and customProof. inputWidget adapts any Var a -> NanoUI Response widget, with a publication policy (OnChange, OnChangeOr, OnlyWhen).

Markdown

nano-ui-markdown parses with commonmark and draws with rich text:

import NanoUI.Markdown

doc = parseMarkdown "# Hello\n\nSome *emphasis* and `code`."

view cache = do
  clicked <- markdown cache doc
  for_ clicked $ \url -> openUrl url

Allocate cache <- newMarkdownCache once. markdown returns the link clicked this frame. For streaming, append without reparsing the whole document:

doc <- useStream stream replyId emptyMarkdown $ \update ->
  onToken client (\token -> update (appendMarkdown token))
void (markdown cache doc)

When appending on the UI thread, append a frame’s tokens in one call. The parser reparses only the tail block, with a few documented exceptions (a long unsplittable final block, or a link-reference definition). MarkdownConfig.mdBlock overrides block drawing, for example to syntax-highlight code.

SVG export

nano-ui-svg has two levels:

  • NanoUI.Draw.Svg exports DrawOp sequences: drawOpsToSvg bounds ops or renderDrawOpsSvg config.
  • NanoUI.Draw.FrameSvg re-renders a whole frame: frameToSvg config ctx input drawData.
import NanoUI.Draw.FrameSvg (defaultFrameSvgConfig, frameToSvg)
import NanoUI.Internal.Context (setDrawExternalText, setDrawSquareGeometry)
import NanoUI.Testing (newPixelContext, runFrame)
import NanoUI.Testing.Harness (withInputOff)

exportViewToSvg view = do
  ctx <- newPixelContext
  let inp = withInputOff 1280 800
  setDrawSquareGeometry ctx True
  setDrawExternalText ctx True
  (_, drawData, _) <- runFrame ctx inp view
  frameToSvg defaultFrameSvgConfig ctx inp drawData

setDrawSquareGeometry makes widget edges axis-aligned; setDrawExternalText moves text onto the raster spans the exporter reads. Without them the export still renders, but rounded edges approximate and drawing text is missing. This is the path used for the interactive specimens in this book and for visual regression tests.

1. Layout shifting & jitter

A label whose text changes length moves its siblings every frame

A counter going 9 -> 10 -> 100, a timer, or a byte total changes the label’s natural width, which re-flows the row on every tick.

Fix: pin the label to the width of its widest expected value:

labelWith (fixedW 48 . alignEnd) (fmtInt count)

This is a recurring fix in stronghead (“fix markers count to fixed width”) and in dashboards generally.

A long value inside a scrolling list widens the whole list

One long row increases the column’s natural width, the list grows a horizontal scrollbar, and the bar appears and disappears as wide rows enter and leave.

Fix: make the cell fill its column instead of contributing natural width, and ellipsize the text:

-- In a row, a label too narrow for its text cuts it off rather than wrapping.
nameLine f = rowWith (fillW . tight) . labelWith (fillW . f)

Inside a scrolling list, cells should be fillW, not sized by content.

A drop-down clips its longest option

A fixed width guessed for a select breaks when an option is long ("Unknown disk · 113 apps · 9.24 GB").

Fix: measure the options with the font and add the chrome:

let w = maximum (0 : map (lineWidth fm) options) + 56
selectWith (fixedW w) options selectedVar

Content-derived geometry recomputes and jitters

Tree column widths, row heights, and pane splits that are derived from the current content every frame move when the content changes.

Fix: lock the geometry in saved layout state (ned’s “grid size locking”) or key constants off the content type, not the text. For a row height, use a constant; for a pane split, store the user’s chosen size.

flex around the wrong child

flex still works, but the clearer pattern is to make the one growable child fillW directly. stronghead replaced fixedW 90 + flex around a filter box with fillW, which also removed dead space.

2. Double borders & box in a box

nano-ui fills padded containers with the panel color, and scrollArea, panel, and card each draw their own background, border, and radius. Nesting them inside popups, dialogs, and panes draws a box inside a box.

Symptoms:

  • A scrollArea in a popup shows a bordered well inside the dialog.
  • A dialog has two concentric borders.
  • A pane with a panel inside a card looks recessed twice.

Fix: one level supplies the chrome.

  • Give the outer dialog padAll 0 and move the padding to the inner columnWith (fillW . padAll 12 ...).

  • Or strip the inner surface:

    styled (inputStyle (background colorTransparent . borderWidth 0)) ...

  • Set themeFloatingWindow and themePopup to the panel surface, so a padded body does not show a panel box inside the dialog.

  • Between two chrome regions, draw one separator at the seam, not a border on the bottom of one and the top of the other.

The stronghead fix was named “Remove duplicate borders from workspace popovers and notifications”; the same change appears in winget-gui’s dialogs.

3. Text metrics & the pixel grid

Glyphs drift over a long run

fmAdvance per glyph multiplied by the character count is not the shaped width of a run. A shaping backend lays a run out by unrounded advances (8 vs 8.25 px at size 15), so per-glyph arithmetic drifts a cell every ~32 characters and long runs overdraw what follows.

Fix: measure the whole run:

lineWidth fm run

ned fixed this as “text stays on the cell grid along a long run”.

Text shimmers at fractional DPI scales

At 125% scaling, rows of 22.4 px stack as 22, 23, 22, 23 and text shimmers while scrolling. Positions and row heights must be whole device pixels.

Fix: snap with the font’s snap scale:

snap v = let k = max 1 (fmSnapScale f) in fromIntegral (round (v * k) :: Int) / k

winget-gui’s rowButton is the reference implementation.

Box-centred is not optically centred

A two-line block with a large label over a small one centres by line boxes, which leave more room under the smaller line; it reads ~4 px high. For exact optical centring, centre on the ink: measure the ink span and the capital/x-height midpoints from FontMetrics glyphs.

alignMid on a row positions the row, not its contents

alignMid on a row positions the row itself in its parent. Centring the row’s contents takes the modifier on each child (or alignMid in the child’s layout). This is the “header dead space” fix in stronghead.

4. Stale cached drawings

A custom-drawn widget has no text spans and no automatic diff of its inputs. Without a content key, its ops are rebuilt and diffed every frame. With a key, unchanged frames skip both, and a key that misses an input shows stale pixels.

The drawing freezes on an input the key missed

winget-gui’s sort arrow stayed on the old column until the key covered everything the drawing read.

Fix: include every input in the key: values, colors, text, theme, scroll viewport width, animation state.

drawingVersioned (contentKey [round sortCol, round scrollY, fromEnum theme]) $ \dc -> ...

If a keyed drawing shows stale pixels, the key is missing an input; the widget is not broken.

A pinned overlay keeps its first frame’s ops

A drag ghost pinned under the pointer with pinAt mx my never changes its layout rectangle, so an unversioned drawing caches the frame it appeared in (ned’s “tab ghost”).

Fix: give it an explicit version that includes what moves it:

drawingVersioned (contentKey [round mx, round my]) $ do
  drawDragGhost

Widths from the scroll viewport belong in the key

ned’s finder rows clamp to rectW (scrollViewport metrics) and key on it, so the drawing follows the viewport when the scrollbar appears.

5. Scroll details

Content runs under the scrollbar

The scrollbar keeps a lane out of the viewport. A wide row drawn to the widget’s full width runs beneath the bar. Clamp content and hit targets to the viewport width, but keep the backdrop filling the widget or its edge shows as a seam down the lane (ned’s “hold the finder’s rows out of its scrollbar’s lane”).

The wheel step does not match the row height

The default notch (~60 px) jumps about one row of 54 px or three smaller rows. Set the wheel step per scroller so a notch is exactly one row:

ctx <- askContext
liftIO $ setScrollTuning ctx defaultScrollTuning
  {scrollWheelStep = rowHeight, scrollSmoothTime = 0}

A scroller can also set its own step with setScrollStepUi; 0 returns it to the context step.

6. Focus and input ordering

Focus questions at the top of the view always say “no”

The node arena is reset before the view runs. isFocused (and any check of editing state) at the top of appView answers False every frame.

Symptom: Ctrl+A selects every item while the search box is being typed into; Delete opens the uninstall dialog.

Fix: read focus and place shortcuts at the end of the view, after the widgets have run:

appView = do
  searchResp <- searchInput' query
  -- ... all widgets ...
  searching <- isFocused (respId searchResp)
  when (not searching) $ whenM (shortcut (key KeyDelete)) deleteSelected

This was winget-gui’s worst input bug.

Escape behind the same guard as Ctrl+A

Text inputs do not claim Escape. If Escape shares the “a field is editing” guard with Ctrl+A and Delete, Escape can never clear a selection once a field has focus.

Fix: give Escape its own condition. It must keep working while a field is focused.

Typed keys never reach a custom widget

A focused widget that reads inputChars must call useInputMethod every frame it accepts text, even when it is not a text field. ned’s file tree takes vim’s j/k as typed text; only the editor asked for input, so the keys never reached the tree.

Fix:

-- Every frame the widget accepts text:
preedit <- useInputMethod wid InputNormal caretRect
for_ preedit drawCompositionAtCaret

A slow leftward drag selects one character

The drag anchor must be taken from the press, not re-derived from the selection each frame. A one-character selection’s anchor sits on its left, so re-deriving it carries the anchor along and selects one character (ned’s “slow leftward drags”).

A widget that appears next frame cannot be focused this frame

requestFocus resolves after layout, but only for widgets declared on that pass. If a field appears because of a state change, request focus on the pass that declares it (store a focusPending flag). See Keyboard, Focus & IME.

Conditional widgets shift ids

A branch that declares different widgets than its alternative changes the id count for everything after it; widgets appear to swap caret state. Wrap the branch in scope, and keep overlays unconditional. See Widget Identity & Keys.

7. SVG export

When exporting with nano-ui-svg:

  • Several canvas drawings in one frame emit colliding clip_/grad_ element ids. Scope them per drawing (prefix each <g><defs> block with an index), as stronghead does.
  • Right-aligned numerals lose their anchor: text-anchor/textLength may need post-processing, and tabular numbers help readouts (font-variant-numeric: tabular-nums at the root).

Quick checklist

  • liftIO (newVar ...) inside a view: allocates every pass. Move it to setup.
  • Unguarded side effects: the view re-runs. Wrap them in whenM (button ...).
  • Conditional widgets or useVars without scope; keyed lists using indices.
  • Overlays called conditionally instead of unconditionally with a Var Bool.
  • useTask inside a tab or branch: the task is cancelled when hidden.
  • keepAnimating at an always-run top level: a busy loop. Call it in the animating widget; use wakeAfter for timers.
  • Writing a freshly computed NaN to a Var Float: NaN /= NaN, so it redraws forever. Guard the write.
  • A custom widget’s content key missing an input: stale pixels or a frozen drawing.
  • A changing label without fixedW: its siblings shift every frame.
  • A wide cell in a scrolling list without fillW: the list scrolls sideways.
  • A scrollArea / panel / card nested in a popup: a box inside a box.
  • Focus queries at the top of the view: the arena was reset; read them at the end.
  • Escape behind the same guard as Ctrl+A/Delete: text inputs do not claim Escape.
  • A focused widget reading inputChars without useInputMethod: typed text never arrives.
  • Per-glyph advance × count for a long run: use lineWidth.
  • Parsing or rebuilding documents per frame: parse once and keep the result outside the view.
  • readVar above the widget that edits the Var: an extra pass per change.
  • Missing -threaded.
  • Touching Context from a worker thread: wake with askWake instead.

Architecture & Internals

Reference for how a frame executes and how applications are structured around it. It explains the cost model behind readVar, focus, and damage; a view does not need any of it to work.

The frame lifecycle

Each frame:

  1. View execution. The NanoUI () action runs top-to-bottom, appending layout nodes, reading input, and reading/writing Vars.
  2. Re-run check. If a Var was written after it was read this pass, the action runs again with one-shot input events cleared.
  3. Layout solve. Flex weights, gaps, padding, and constraints produce a rectangle for every node.
  4. Hit testing and focus. Pointer coordinates, shortcuts, hover, press, and Tab order resolve against the new geometry.
  5. Damage calculation. The new geometry and draw ops are diffed against the previous frame.
  6. Paint. Only the damaged region is rasterized and presented.

The view runs before layout, so respRect is the previous frame’s rectangle. Focus is resolved after the view, so a focus request takes effect next frame.

Consequences

  • The view can run more than once per frame. A write to a Var read earlier in the pass triggers a second pass with one-shot events cleared. Guard side effects with an event (whenM (button ...)), and never allocate frame-lived resources inside the view.
  • readVar placement is a performance decision. Reading below the input that edits a value keeps a change to one pass; reading above costs a second pass. A Var bound to a widget with no readVar repaints only that widget; a readVar promotes the change to a full-window repaint.
  • Geometry lags one frame. respRect is empty on a widget’s first appearance. Tests warm up before targeting rectangles.
  • Widget ids are positional. Conditional widgets, reordered lists, and conditional overlays change the count and therefore later ids. scope and withKey keep the counts stable; see Widget Identity & Keys.
  • Idle costs zero. With no animation, timed wake, task, or input, the loop blocks on the OS event queue. Do not dirty the context every frame to force redraws.

Application patterns

Three real applications (ned, stronghead, winget-gui) converge on the same architecture; the difference is where durable state lives. All of them follow the core rule: setup once in IO, then run.

main :: IO ()
main = do
  cache <- newViewCache
  env   <- newAppEnv
  runSdlApp defaultSdlOptions (appView env cache)

Pattern A: one domain state and a wake channel

winget-gui keeps package-manager results in one IORef and snapshots it at frame start:

data Env = Env
  { envState :: IORef AppState
  , envWake  :: IORef (IO ())
  }

appView env = do
  wake <- askWake
  liftIO $ writeIORef env.envWake wake
  state <- liftIO $ readIORef env.envState
  mainLayout state

-- worker thread
atomicModifyIORef' env.envState (\s -> (s {packages = results}, ()))
wake <- readIORef env.envWake
wake

Gather every read into one Frame record before building the window, memoize derived collections in IORef (Maybe (key, value)) caches keyed by a revision counter, and read shortcuts after the widgets. Use this when the domain state is shared with workers, a database, or a protocol.

Pattern B: an app record of Vars

stronghead has many independent panels, each with its own view state:

data App = App
  { filterText   :: Var Text
  , activeTab    :: Var TabId
  , zoomLevel    :: Var Float
  , isInspecting :: Var Bool
  }

newApp = App <$> newVar "" <*> newVar TabOverview <*> newVar 1.0 <*> newVar False

Panel modules take the slice they own. Use this when the application is mostly interactive UI state with little external I/O.

Pattern C: application-owned state

ned keeps a plain IORef App; the toolkit knows nothing about it. The view projects slices and re-reads after anything that may change the model:

editorView (Editor ref) = do
  app <- liftIO (readIORef ref)
  renderEditor app
  app' <- liftIO (readIORef ref)
  when (viewChanged app app') requestFrame

requestFrame asks for one more frame when what was drawn no longer matches the state. Use this for editors, terminals, games, and models that already exist as a library. It is an escape hatch, not a replacement for Var dependencies.

Choosing

The application…Pattern
Has one domain state, uses worker threads, runs commandsA: IORef + askWake
Is a large set of interactive panes and toolsB: record of Vars
Has a model that predates the UI or is shared with a libraryC: app-owned IORef + requestFrame
Is a state machine with explicit transitionsElm-style (nano-ui-emit)
Is a small toolWhatever is simplest; a handful of useVars is fine

Patterns mix. An IORef domain state with Var view state is normal; an Elm reducer can sit inside one pane of a Var-based application.

The shared view discipline

  1. Read state once at the top, or immediately before the subtree that uses it.
  2. Build top-to-bottom. Layout is solved after the view.
  3. Read after the parts that may write.
  4. Run keyboard and focus queries last.
  5. Guard effects with events. The view can run more than once per frame.
  6. Keep derived values derived. Cache expensive work by revision, not by copying fields.
